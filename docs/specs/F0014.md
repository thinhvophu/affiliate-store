# Feature Specification: Launch Technical Readiness

**ID:** `F0014`
**Epic/Module:** Platform — Measurement, CI Gates & Launch Verification
**Status:** Approved

---

## 1. Business Objective

The same production-readiness audit (2026-08-12) that produced `F0013` found the application code in good shape — clean build, 33 fully static pages, every SEO chokepoint implemented — but the **measurement and verification layer around it missing**. Four gaps, none of them large, each of which costs real money or real safety after launch:

1. **No analytics at all.** `F0007` (Analytics & Click Tracking) is scoped in the backlog but has **no spec file and no user stories**, and nothing was ever built: `grep` for `gtag` / `affiliate_click` returns zero hits in application code. `lib/env.ts` reads `NEXT_PUBLIC_GA_MEASUREMENT_ID` and `<AffiliateLink>` already emits the four contract `data-*` attributes the listener was designed for — the seam exists, the consumer does not. Launching without it means no way to know which products convert, which posts drive traffic, or whether the affiliate CTAs are clicked at all.
2. **Tests are never run in CI.** 121 tests across 15 files pass locally, but `.github/workflows/ci.yml` runs only `typecheck`, `lint` and `build`. Every guard the project relies on — the JSON-LD escaping test, the affiliate-URL allow-list tests, the ingestion tests, and the new content guards `F0013` is adding — can regress on a green PR.
3. **No Search Console property.** `docs/spec.md` §9 lists sitemap submission as a launch-day item; nothing in the repository indicates verification has happened. Without it there is no index coverage data, no crawl-error reporting, and no query data.
4. **Formatting has drifted.** `npm run format` fails on **126 files**. It is not in CI, so the drift is invisible and every future diff carries unrelated whitespace noise.

This feature closes all four. It is the technical counterpart to `F0013` (which fixes content data) and, together with it, constitutes the remaining pre- and at-launch work.

**Relationship to `F0007`:** `F0007` — Analytics & Click Tracking never received a spec or stories. **US00143 and US00144 below deliver `F0007`'s entire scope verbatim** (GA4 component conditionally rendered, never loaded in development, `affiliate_click` event with `product_name` / `product_category` / `destination_url`, hooked into the centralized `<AffiliateLink>` from `F0003`). `F0007` is considered implemented when they ship; it gets no separate spec file.

## 2. Scope

### In Scope

- A GA4 integration mounted in the root layout, rendered **only** when `NEXT_PUBLIC_GA_MEASUREMENT_ID` is set and **never** in development.
- A delegated `affiliate_click` GA4 event fired on every affiliate-link click, sourced from the existing `F0003 ↔ F0007` `data-*` contract on `<AffiliateLink>` — no per-call-site changes.
- A `test` job added to the PR validation workflow so the suite actually gates merges.
- A `format` job added to the same workflow, plus a one-time repository-wide `prettier --write` baseline.
- Google Search Console property creation, ownership verification, and sitemap submission — including the code path (an optional env var surfaced through `lib/seo.ts`) if meta-tag verification is chosen over DNS.

### Out of Scope

- **Google AdSense integration.** `docs/spec.md` §2 marks display ads P1 and no feature owns them; this feature only ships the analytics half of measurement. AdSense remains unowned.
- A custom analytics backend, A/B testing, cookie-consent UI, or any GA configuration beyond the measurement ID (inherited from `F0007`'s original out-of-scope list).
- Content and catalog fixes — those are **F0013**.
- Changing the SSG-only constraint. Every addition here must leave all routes statically pre-rendered (`○` / `●`, never `ƒ`).
- Adding a Prettier _plugin_ or changing the formatting ruleset — US00142 applies the existing config, it does not redesign it.

## 3. Process Flow

1. **US00141 and US00142 first** (independent, low risk): the test and format jobs land, and the formatting baseline is applied as an isolated commit — so every later PR in this feature and in `F0013` is gated and produces a clean diff.
2. **US00143** adds the GA4 component behind the env var. With the var unset (the current state), the deployed output is byte-for-byte unchanged — verifiable before any measurement ID exists.
3. **US00144** adds the delegated `affiliate_click` listener on top of it, consuming `data-affiliate-link` / `data-product-name` / `data-product-category` / `data-destination-url`.
4. The measurement ID is created in GA4 and set on Vercel Production; a deploy is triggered; events are confirmed arriving in GA4 Realtime by clicking a real affiliate card.
5. **US00145** runs at launch: create the Search Console property for the production domain (which `F0013`/US00131 has by then confirmed), verify ownership, submit `/sitemap.xml`, and confirm the reported URL count matches the sitemap.

## 4. User Stories & Acceptance Criteria

### US00141: Test suite gated in CI

**As a** contributor,
**I want to** the Vitest suite to run on every pull request,
**So that** a regression in an affiliate, schema, ingestion or content guard fails the PR instead of reaching `main`.

**Acceptance Criteria:**

- **Scenario 1:** Tests run on every PR
  - `Given` a pull request against the repository
  - `When` CI runs
  - `Then` a `test` job executes `npm test` alongside the existing `typecheck`, `lint` and `build` jobs

- **Scenario 2:** A failing test blocks the merge
  - `Given` a change that breaks any existing test
  - `When` CI runs on its PR
  - `Then` the `test` job fails and the PR is not mergeable — verified by deliberately breaking a test on a scratch branch and confirming the red run

- **Scenario 3:** The job matches the existing workflow conventions
  - `Given` the new job in `.github/workflows/ci.yml`
  - `When` it is compared to the existing jobs
  - `Then` it uses the same `actions/checkout@v4` + `actions/setup-node@v4` with `node-version-file: ".nvmrc"` and `cache: "npm"` + `npm ci` shape, and runs in parallel with the others rather than serially

### US00142: Formatting baseline & CI gate

**As a** reviewer,
**I want to** every diff to contain only meaningful changes,
**So that** review is not diluted by whitespace churn from an unformatted repository.

**Context:** `npm run format` currently reports style issues in **126 files**, spanning `app/`, `components/`, `lib/`, `scripts/` and `docs/`. Because no CI job runs it, the drift is invisible and grows.

**Acceptance Criteria:**

- **Scenario 1:** Repository is formatted
  - `Given` the repository after this story
  - `When` `npm run format` runs
  - `Then` it exits zero with no files reported

- **Scenario 2:** Formatting is gated on PRs
  - `Given` a pull request containing an unformatted file
  - `When` CI runs
  - `Then` a `format` job fails naming the offending file, so drift cannot re-accumulate

- **Scenario 3:** The baseline commit does not pollute history
  - `Given` the repository-wide reformat
  - `When` it is committed
  - `Then` it is an isolated commit containing **only** formatting changes (no behavioral edits), and its SHA is recorded in a `.git-blame-ignore-revs` file so `git blame` stays useful

- **Scenario 4:** The reformat changes no behavior
  - `Given` the formatting baseline commit
  - `When` `npm run typecheck`, `npm run lint`, `npm test` and `npm run build` run against it
  - `Then` all pass, and the build output's route table is unchanged from before the commit

### US00143: GA4 integration, environment-gated

**As a** site owner,
**I want to** Google Analytics 4 loaded on the production site only when a measurement ID is configured,
**So that** I can see traffic from launch day without shipping a tracker into development or into a build that has no ID.

**Acceptance Criteria:**

- **Scenario 1:** Analytics loads when configured in production
  - `Given` `NEXT_PUBLIC_GA_MEASUREMENT_ID` is set on the production environment
  - `When` any page of the production build is loaded
  - `Then` the GA4 script is present and initialized with that measurement ID, and a `page_view` is recorded in GA4 Realtime

- **Scenario 2:** No ID means no tracker, and no output change
  - `Given` `NEXT_PUBLIC_GA_MEASUREMENT_ID` is unset or empty (today's state)
  - `When` the site is built and served
  - `Then` no GA script tag, no `gtag` global and no analytics network request is present anywhere in the output — the rendered HTML is functionally identical to the pre-feature build

- **Scenario 3:** Never in development
  - `Given` the app running under `npm run dev`
  - `When` any page is loaded, even with a measurement ID set in `.env.local`
  - `Then` no analytics script is loaded and no event is sent, so local browsing never pollutes production data

- **Scenario 4:** Static rendering is preserved
  - `Given` the analytics component mounted in the root layout
  - `When` `npm run build` runs
  - `Then` every route is still pre-rendered (`○` or `●`, no `ƒ`), and no route is flipped to dynamic rendering by the addition

### US00144: `affiliate_click` event tracking on every affiliate link

**As a** site owner,
**I want to** every affiliate link click reported to GA4 with the product's name, category and destination,
**So that** I can identify top-converting products without relying on Shopee's own dashboard.

**Context:** `<AffiliateLink>` already emits the `F0003 ↔ F0007` contract attributes — `data-affiliate-link` (presence flag), `data-product-name`, `data-product-category`, `data-destination-url`. `CLAUDE.md` declares these a public API: renaming any of them is a breaking change that must update both `<AffiliateLink>` and this listener in the same PR, and no other component may emit `data-affiliate-link`.

**Acceptance Criteria:**

- **Scenario 1:** Every affiliate surface reports clicks
  - `Given` an affiliate link on any surface — product card, product-detail CTA, related products, homepage featured, or an inline `<ProductCard>` in a post
  - `When` it is clicked
  - `Then` a GA4 `affiliate_click` event is sent carrying `product_name`, `product_category` and `destination_url` read from the element's `data-*` attributes, with no per-surface or per-call-site code

- **Scenario 2:** Navigation is never blocked or delayed
  - `Given` an affiliate link click
  - `When` the event is dispatched
  - `Then` the link still opens its Shopee URL in a new tab immediately (`target="_blank"` means the current document is not unloaded, so no beacon/`unload` workaround is needed), and a failure or absence of analytics never prevents or delays the navigation

- **Scenario 3:** Disabled analytics is a silent no-op
  - `Given` `NEXT_PUBLIC_GA_MEASUREMENT_ID` is unset
  - `When` an affiliate link is clicked
  - `Then` nothing is sent, no console error is produced, and the click behaves exactly as it does today

- **Scenario 4:** One event per click
  - `Given` a whole-card affiliate link (the US00032 pattern, where the entire card surface is one anchor)
  - `When` the user clicks the card body, the image, or the CTA span
  - `Then` exactly one `affiliate_click` event is sent — nested elements inside the anchor do not produce duplicates

### US00145: Search Console verification & sitemap submission

**As a** site owner,
**I want to** the production domain verified in Google Search Console with its sitemap submitted,
**So that** I get index coverage, crawl errors and query data from the first day of indexing.

**Acceptance Criteria:**

- **Scenario 1:** Property verified for the production domain
  - `Given` the production domain (confirmed by `F0013`/US00131)
  - `When` a Search Console property is created and ownership verified
  - `Then` verification succeeds and persists across deploys — via DNS TXT record (preferred: no code change, survives any hosting change) or, if DNS is unavailable, a verification meta tag

- **Scenario 2:** Meta-tag verification respects the metadata chokepoint
  - `Given` meta-tag verification is chosen instead of DNS
  - `When` the tag is added
  - `Then` it is sourced from a new optional env var declared in `lib/env.ts` and emitted through `buildRootMetadata()` in `lib/seo.ts` — no route or component hand-writes a `<meta name="google-site-verification">` tag, per the existing "page metadata is built in one place" rule

- **Scenario 3:** Sitemap submitted and accepted
  - `Given` a verified property
  - `When` `/sitemap.xml` is submitted
  - `Then` Search Console reports it as successfully read with no fetch error, and the discovered URL count matches the sitemap's entry count (29 at audit time, subject to `F0013`'s changes)

- **Scenario 4:** No unintended crawl blocks
  - `Given` the deployed `/robots.txt`
  - `When` it is fetched and tested against Search Console's URL inspection for one product, one post and one category URL
  - `Then` all three are reported crawlable and the sitemap pointer in `robots.txt` uses the production domain

## 5. Edge Cases & Error Handling

- **Measurement ID set but invalid:** GA silently drops the data rather than erroring. Scenario 1 of US00143 is verified against GA4 Realtime, not merely against the presence of a script tag — a script tag alone proves nothing.
- **Ad blockers / tracking protection:** a meaningful share of Vietnamese users block GA. The `affiliate_click` count is therefore a **lower bound**, not a true click count, and must not be treated as authoritative against Shopee's own dashboard. Analytics failing to load must never affect link behavior (US00144 Scenario 2).
- **Middle-click, ⌘/Ctrl-click, and context-menu "open in new tab":** these do not all fire a `click` event. Under-counting from these paths is accepted; double-counting is not (US00144 Scenario 4).
- **`data-*` contract drift:** if `<AffiliateLink>`'s attribute names ever change, this listener breaks silently — events keep firing with `undefined` fields rather than throwing. The `CLAUDE.md` rule ("renaming is a breaking change; update both in the same PR") is the only guard; a test asserting the listener reads the same names `<AffiliateLink>` writes is the cheap reinforcement.
- **The formatting baseline colliding with in-flight `F0013` branches:** land US00142 before or after `F0013`'s content work, not in the middle of it — a 126-file reformat will conflict with any open branch touching the same files.
- **CI cost of a fourth and fifth job:** all jobs already run `npm ci` independently; adding two more roughly doubles install work. Acceptable at this repository size; if it becomes slow, the fix is job consolidation, not dropping the gates.
- **Search Console verification lost on domain or host change:** DNS TXT verification survives a Vercel project change; a meta tag does not survive an env var being cleared. This is why DNS is the preferred path in US00145 Scenario 1.

## 6. Technical Considerations

- **Read the Next.js docs first.** Per `AGENTS.md`, consult `node_modules/next/dist/docs/` before implementing US00143 — the correct integration for the installed Next.js 16 is what the docs say, not what training data suggests. The two candidate approaches are `@next/third-parties/google`'s `<GoogleAnalytics>` (a new dependency, not currently installed) and a hand-rolled `next/script` component; the implementation plan picks one **after** reading the docs, and states why.
- **Analytics must not break SSG.** The project is SSG-only (`CLAUDE.md`); `US00099` was deliberately deferred rather than accept a single dynamic route. Any analytics component is a client component mounted in the root layout — it must not introduce a request-time API, and US00143 Scenario 4 checks the route table explicitly.
- **The click listener is delegated, not per-link.** One listener on `document` matching `closest("[data-affiliate-link]")` — this is precisely why the `F0003 ↔ F0007` contract was designed as data attributes rather than an `onClick` prop, and it means zero changes to `<AffiliateLink>`, `<ProductCard>`, `<MdxProductCard>` or any consumer. It also keeps `<AffiliateLink>` a Server Component.
- **`target="_blank"` removes the hard part.** The classic outbound-click problem (event racing page unload, needing `navigator.sendBeacon` or `transport_type: beacon`) does not apply here, because the current document stays alive. Do not add unload-based workarounds.
- **The env var is already typed.** `lib/env.ts` exposes `NEXT_PUBLIC_GA_MEASUREMENT_ID` via `optionalEnvVar` and `.env.example` documents it — US00143 consumes the existing plumbing rather than adding its own `process.env` read.
- **Search Console meta tag, if used, goes through `lib/seo.ts`.** `CLAUDE.md`: "Page metadata is built in one place." Next.js `Metadata` has a first-class `verification.google` field — it belongs in `buildRootMetadata()`, fed by a new optional entry in `lib/env.ts`, not hand-written into `app/layout.tsx`.
- **US00141 is a prerequisite for `F0013`'s test-based guards.** `F0013`'s word-count, duplicate-cover and empty-category checks are only real gates once the suite runs in CI. If `F0013` lands first, those guards are advisory until this story ships — worth sequencing US00141 early.
- **Verification is partly outside the repository.** US00143/US00144 need a GA4 property and a deploy to confirm; US00145 is entirely a console operation. These stories are not "done" at merge — they are done when the events and the sitemap report are observed in the respective consoles, and that observation should be recorded in the PR.
