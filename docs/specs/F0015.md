# Feature Specification: Weekly Deal Roundup Content

**ID:** `F0015`
**Epic/Module:** Content Operations — Recurring Deal Content
**Status:** Draft

---

## 1. Business Objective

The existing content pipeline (`F0012`) grows the catalog and closes post gaps, but every post is a one-off buying guide tied to already-ingested `Product` fixtures — which requires `specifications`, and the `shopee-affiliate` scrape tool's spec extraction (`scraper/product.ts`, regex-parsed out of the free-text product description) is unreliable enough that scraped candidates are rejected by `validateCandidate` almost every time (`scripts/ingest/sources/deal-schema.ts` comment, confirmed 2026-07-26/07-26). Meanwhile the scrape tool already does something the site doesn't use yet: `processor/ranker.ts`'s `rankDeals()` filters (discount ≥20%, rating ≥4.5, sold ≥100) and scores (`discount% × 2 + rating × 10 + log10(soldCount) × 5`) every search result and returns a pre-ranked top N, with real affiliate links resolved only for that top N via the Shopee Affiliate batch-link API.

This feature turns that already-ranked data into a recurring content format: a weekly "Top X `<category>` deal trên Shopee" post per category, generated straight from ranked deal data — no `Product` fixture, no specs requirement. Because it's a _recurring_ post targeting the same head keyword every week, it also has to solve the keyword-cannibalization problem that plain repetition would cause: the newest post reads as the live "this week" roundup, and the previous week's post is relabeled with its specific publish date once superseded, so only one URL per category ever competes for the generic query at a time.

## 2. Scope

### In Scope

- A new script (`scripts/generate-deal-post.ts` or slash command, mirroring `scripts/scaffold-post.ts`'s CLI shape) that:
  - Calls the `shopee-affiliate` `scrape_products` tool with a category's configured keyword(s) and a `top_n`, and consumes the tool's **own** ranking (`rankDeals()`'s discount/rating/sold-count score) — this feature does **not** re-implement deal ranking.
  - Writes `content/posts/<slug>.mdx` for the current week's roundup, in the _evergreen_ framing ("Top X `<keyword>` Deal Trên Shopee Tuần Này" — no date in the visible H1/title).
- A new MDX-embeddable component, `<DealCard slug="…" />`-equivalent (renders directly from the week's saved deal data — name, price, `originalPriceVnd`, `discountPercent`, image, resolved `affiliateUrl` — no `Product` fixture, no specs), following the existing whole-card `<AffiliateLink>` pattern (`AffiliateLink.module.css`'s `.card`) so it carries the same F0003↔F0007 `data-*` click-tracking contract as `<ProductCard>`.
- A build-time `assertAffiliateUrl` check on every deal's `affiliateUrl` before it's rendered — the same gate `lib/products.ts` applies for `Product` fixtures, just applied at generation time here since there's no product loader in this path.
- Supersession handling: when a new week's roundup for a category is generated, the **previous** roundup post for that same category is rewritten in place — H1, `<title>`/meta title, and lead paragraph updated to name its specific publish date (dd/mm/yyyy) instead of "tuần này" — and dropped from "latest/related" surfaces that would otherwise link to two same-keyword posts at once.
- A static "giá có thể thay đổi tại thời điểm bạn xem" (price may have changed since publish) disclaimer rendered on every deal-roundup post, next to the existing affiliate disclosure.
- Reuse of every existing per-post SEO/build chokepoint unchanged: `/bai-viet/[slug]/` route, `PostBody`, `buildArticleSchema`, breadcrumbs, canonical/OG — this feature adds a new **embeddable component** and a new **generation script**, not a new route or a new SEO code path.

### Out of Scope

- Re-implementing or tuning the scrape tool's ranking/filter thresholds — `rankDeals()`'s defaults (discount ≥20%, rating ≥4.5, sold ≥100) are accepted as-is; changing them means changing the `affiliate-tool` repo, not this one.
- Fixing the scrape tool's spec-extraction reliability — this feature's entire point is to route around that gap, not patch it.
- Cron/scheduled automation of the weekly run (unlike `.github/workflows/scheduled-deploy.yml`) — v1 is operator-triggered, same convention as `/scrape-ingest` and `/write-post`. Scheduling is a candidate follow-up once the manual flow is proven.
- `noindex`-ing or otherwise deindexing archived (superseded) roundup posts — v1 relies on the H1/title/lead-paragraph rewrite plus dropped internal linking to stop active cannibalization; a stronger deindex policy is a candidate follow-up if archived posts are still observed competing in Search Console.
- Ingesting deal-roundup products into the permanent catalog (`content/products/*.json`) — a stand-out deal a human wants to keep long-term still goes through the normal `F0012` ingest pipeline separately.
- Any change to `processor/ranker.ts`'s LEGO-brand special case or other category-specific filtering inside the scrape tool.

## 3. Process Flow

**This flow is built once and then invoked repeatedly** — once per category, once per week, indefinitely. US00146–US00149 deliver the reusable mechanism (script/command + supersession logic), not a single post; the recurring cadence itself is ongoing operator work after this feature ships, the same relationship `F0012`'s `scaffold:post` has to actually scaffolding a post every time there's a content gap.

1. An operator runs the generation script/slash command naming a registered category and its search keyword(s) (mirroring `ingest:products`' `--category`/`--query` shape), e.g. `--category=chuot-gaming --query="chuột gaming không dây" --top=5`.
2. The script calls `mcp__shopee-affiliate__scrape_products({ keywords, top_n })`, which internally ranks and returns the top N deals plus resolved affiliate links, saved to `data/deals/<date>.json` (same file the `F0012` ingest pipeline already reads).
3. The script validates every returned deal's `affiliateUrl` via `assertAffiliateUrl` — a deal whose link fails the host allow-list is dropped from the roundup (not fatal to the whole run) and named in the summary.
4. The script checks whether a roundup post already exists for this category from a prior run:
   - If none exists, it writes a new `content/posts/<slug>.mdx` (slug carries the publish date for filename uniqueness) titled/framed as "tuần này."
   - If a prior roundup exists for this category, that file's H1/title/lead paragraph is rewritten to reference _its own_ publish date (archived framing), and a new file is written for the current week in the "tuần này" framing.
5. The new post embeds one `<DealCard>`-equivalent per ranked deal (name, price, discount badge, rating/sold-count, whole-card `<AffiliateLink>`), the required affiliate disclosure, and the price-may-have-changed disclaimer.
6. `npm run build` runs to confirm the new/rewritten posts pass every existing build-time and test guard (word count, `h2` count, embed count, breadcrumbs, JSON-LD).
7. The operator (or the automated end-to-end path, later) commits and publishes per the existing direct-to-`main` convention for recurring content.

## 3a. Story numbering

**Verified 2026-09-07 during implementation planning.** The stories were numbered in the order they were written, and that order already **is** a topological sort of their dependency graph: ascending story number is the execution order, and §3's Process Flow reads 1→7 in sequence. **No renumbering is needed** — unlike `F0014`, whose stories had to be reordered (§3a there, original numbers at commit `82d1fc8`).

The graph is a strict chain, not a tree — every story hard-depends on its immediate predecessor:

| Order | Story   | Delivers                             | Depends on                                                                                                 |
| ----- | ------- | ------------------------------------ | ---------------------------------------------------------------------------------------------------------- |
| 1     | US00146 | Ranked-deal source (read + validate) | —                                                                                                          |
| 2     | US00147 | Deal card, sidecar loader, generator | **US00146 (hard)** — the generator consumes `loadRankedDeals()`'s `RankedDeal[]`                           |
| 3     | US00148 | Supersession + current/archived      | **US00147 (hard)** — needs `lib/deals.ts`'s `postHasDeals()` and the `{/* roundup-lead:… */}` markers      |
| 4     | US00149 | `/deal-roundup` entry point          | **US00146 + US00147 + US00148 (all hard)** — it sequences all three and adds the MCP call none can contain |

**There are no soft/conflict-avoidance orderings here.** Every edge is a real code dependency, so the chain cannot be reordered the way `F0014`'s US00142/US00143 could.

**The one available parallelization.** US00147 splits cleanly in two halves, and only one of them depends on US00146:

- **Rendering half** — `types/deal.ts`, `lib/deals.ts`, `<DealCard>`, `<MdxDealCard>`, `<PriceDisclaimer>`, the `lib/posts.test.ts` and `lib/format.ts` guard edits. Depends on **nothing**; it reads sidecar JSON that a hand-written fixture can supply.
- **Generation half** — `scripts/deal-roundup/{template,writer}.ts` and `scripts/generate-deal-post.ts`. This is the part that needs US00146.

So US00146 and US00147's rendering half may be built concurrently. They touch disjoint files (`scripts/deal-roundup/{deal,source,args,report}.ts` vs `lib/` + `components/`), so there is no merge conflict risk. Everything after that is strictly sequential.

## 4. User Stories & Acceptance Criteria

### US00146: Fetch and consume the scrape tool's pre-ranked deals

**As a** site operator,
**I want to** request the top N ranked deals for a category's keyword(s) from the `shopee-affiliate` scrape tool,
**So that** deal selection reuses the tool's existing discount/rating/popularity scoring instead of re-implementing ranking logic in this repo.

**Acceptance Criteria:**

- **Scenario 1:** Top N deals are returned pre-ranked
  - `Given` a registered category and a keyword, and `--top=5`
  - `When` the script calls `scrape_products({ keywords: [keyword], top_n: 5 })`
  - `Then` it receives exactly the tool's own ranked/filtered result (no re-sorting, re-filtering, or re-scoring performed in this repo) and persists nothing beyond what the tool already wrote to `data/deals/<date>.json`

- **Scenario 2:** Invalid affiliate host is dropped, not fatal
  - `Given` one of the returned deals has an `affiliateUrl` whose host is not in `lib/affiliate.ts`'s allow-list
  - `When` the script validates every deal via `assertAffiliateUrl`
  - `Then` that deal is excluded from the roundup and named in the run summary, while the rest of the roundup is still generated

- **Scenario 3:** Fewer qualifying deals than requested is not an error
  - `Given` a category/keyword combination where the tool's quality filters (discount ≥20%, rating ≥4.5, sold ≥100) leave fewer than `--top` deals
  - `When` the script finishes
  - `Then` it generates a roundup with the deals actually available and reports the shortfall (e.g. "requested 5, got 3"), rather than failing or fabricating placeholder entries

### US00147: Generate the current week's deal-roundup post

**As a** site operator,
**I want to** a weekly "Top X `<category>` deal trên Shopee" post generated directly from ranked deal data, with no `Product` fixture required,
**So that** the unreliable `specifications` field from the scraper never blocks publishing timely deal content.

**Acceptance Criteria:**

- **Scenario 1:** Post renders without a `Product` fixture
  - `Given` a set of validated ranked deals for a category
  - `When` the script writes `content/posts/<slug>.mdx`
  - `Then` the post embeds one deal-card component per deal sourced directly from the deal data (name, price, `originalPriceVnd`, `discountPercent`, image, `affiliateUrl`), and `next build` succeeds with **zero** new `content/products/*.json` files written

- **Scenario 2:** Every deal card preserves the F0003↔F0007 click contract
  - `Given` a rendered deal-roundup post
  - `When` its HTML is inspected
  - `Then` each deal card is a whole-card `<AffiliateLink>` carrying `data-affiliate-link`, `data-product-name`, `data-product-category`, and `data-destination-url` — identical contract to `<ProductCard>`, so `AffiliateClickTracker` fires `affiliate_click` for these clicks with no changes to the tracker itself

- **Scenario 3:** Depth-floor and disclosure guards are satisfied
  - `Given` the generated post
  - `When` `lib/posts.test.ts`'s publish-grade checks run (`US00134`)
  - `Then` it clears `MIN_POST_WORDS`, has ≥2 `h2` sections, and is recognized as having ≥1 qualifying affiliate embed (the depth-floor guard's embed-count check is extended to count the new deal-card component alongside `<ProductCard>`) — and the page renders both the standard affiliate disclosure and the price-may-have-changed disclaimer

### US00148: Supersede the previous week's post on a new run

**As a** site owner,
**I want to** only one post per category ever framed as "this week's" deals, with the prior week's post automatically relabeled to its own specific date,
**So that** the weekly roundups don't cannibalize each other for the same head keyword in search.

**Acceptance Criteria:**

- **Scenario 1:** First run for a category creates the evergreen-framed post
  - `Given` no prior deal-roundup post exists for a category
  - `When` the script runs
  - `Then` a new post is created with H1/title reading "... Tuần Này" (no date) and it is included in whatever "latest posts"/related-post surfaces normally list new posts

- **Scenario 2:** A later run rewrites the prior post's framing, not just its metadata
  - `Given` a category already has a "tuần này"-framed roundup post from a previous run, dated `publishedAt: 2026-08-31`
  - `When` the script runs again for the same category
  - `Then` the existing post's **H1 and lead paragraph** (not only its `<title>`/meta description) are rewritten to name `31/08/2026` explicitly, so the archived page's on-page content — not just its metadata — no longer targets the generic "this week" query

- **Scenario 3:** Only the current post is promoted in internal linking
  - `Given` a category with one current and one or more archived roundup posts
  - `When` any surface that lists/links recent posts (homepage latest-posts strip, blog listing, related-posts) renders
  - `Then` only the current week's post for that category is surfaced there by default; archived posts remain reachable (not deleted, not `noindex`) but are not actively promoted

### US00149: End-to-end weekly generation entry point

**As a** site operator,
**I want to** a single command that runs fetch → validate → generate → supersede → build-verify for a category, safe to re-run every week indefinitely,
**So that** producing each week's roundup is one operation, matching the existing `/scrape-ingest` / `/write-post` convention — this story delivers the recurring mechanism itself, not one post.

**Acceptance Criteria:**

- **Scenario 1:** One command completes the full flow
  - `Given` a registered category and keyword(s)
  - `When` the operator runs the entry-point command
  - `Then` US00146 (fetch/rank), US00147 (generate current post), and US00148 (supersede prior post) all complete, followed by `npm run build` succeeding, without additional manual steps beyond review and `git push`

- **Scenario 2:** A failure partway through does not leave a half-superseded state
  - `Given` a run where deal generation succeeds but the build-verify step fails
  - `When` the operator inspects the working tree
  - `Then` both the new post and any rewritten prior post are visible as uncommitted changes (nothing was pushed), so the operator can fix and retry or discard cleanly — never left with the prior post silently relabeled while no current post exists

## 5. Edge Cases & Error Handling

- **Category has zero qualifying deals this week** (all filtered out by the tool's thresholds): no new post is generated; the prior week's post is **not** superseded (still "tuần này"-framed) so the site never goes a week showing a stale-dated post as current when nothing new was found — script exits reporting the empty result, not an error.
- **Deal that was "top 1" last week no longer appears this week** (price rose, delisted, out of stock): simply absent from this week's list — no diffing/callout required in v1.
- **Two runs for the same category on the same day** (operator re-runs after fixing a keyword typo): idempotent by category, not by date — the second run's "current" post overwrites the first run's "current" post output for that day rather than creating a second archived entry (mirrors `scaffold:post`'s refuse/overwrite discipline, applied per-category-per-run rather than per-slug).
- **Prices/discounts differ between when the tool scored a deal and when a reader clicks days later**: covered by the mandatory disclaimer (§2 In Scope) — this is a UX/compliance necessity for any deal-roundup format, not a defect to engineer around.
- **A deal's `affiliateUrl` host isn't in the allow-list** (tool or Shopee API drift): dropped per-deal (US00146 Scenario 2), never silently rendered with a raw/unvalidated href — no exception to the "no file outside `lib/affiliate.ts` validates affiliate URLs" rule.
- **`rankDeals()`'s LEGO-keyword special case or other tool-side quirks**: this repo treats the tool's output as opaque and authoritative; no attempt to detect or work around tool-side filtering decisions.

## 6. Technical Considerations

- **No new route.** This feature adds a content _pattern_ (a new MDX-embeddable component + a new generation script) inside the existing `/bai-viet/[slug]/` post pipeline — `PostBody`, `buildArticleSchema`, breadcrumbs, canonical/OG all apply unchanged. The only net-new rendering code is the deal-card component and its MDX adapter (parallel to `MdxProductCard`, but reading from the week's persisted deal data instead of `getProductBySlug`).
- **`lib/posts.test.ts`'s depth-floor guard (`US00134`) currently counts only `<ProductCard slug>` for its "≥1 embed" check.** That check must be extended to recognize the new deal-card component too, or every generated roundup post will fail the existing publish-grade test — this is a required, not optional, edit to a `F0013` guard.
- **`assertAffiliateUrl` gate has no natural call site for deal data**, unlike `Product` fixtures where `lib/products.ts` calls it at load time. The generation script itself must call it per deal before rendering (US00146 Scenario 2) — this is new call-site plumbing, not a reuse of an existing hook.
- **Deal data persistence:** the week's deals need to live somewhere the MDX component/adapter can read at build time, since there's no `content/products/*.json` fixture backing them. Options (to be settled during implementation planning, not this spec): embed the deal data directly in the post's frontmatter, or persist a small per-post JSON sidecar under `content/` read by a new `MdxDealCard`-equivalent adapter mirroring `MdxProductCard`'s build-time-throw-on-miss pattern. Either way, the same "no file outside the designated chokepoint parses/rewrites this data" discipline applies.
- **Supersession is a content rewrite, not a new mechanism.** US00148 is implemented as the script editing an existing `.mdx` file's frontmatter/H1/lead paragraph in place — no new "post status" field, no CMS-like state machine. This keeps the feature consistent with the project's file-is-the-database model.
- **`data/deals/<date>.json` is already a committed audit-trail directory** (`F0012`/US00124) — this feature's scrape calls land in the same directory with no new storage convention needed.
- **Relationship to `F0012`:** this feature is additive and deliberately does not touch `ingest:products`, `scaffold:post`, or the `Product` ingestion path — a deal that proves worth keeping long-term still goes through the existing pipeline as a separate, human-decided step (§2 Out of Scope).
- **Relationship to `F0014`:** click tracking is inherited for free (US00147 Scenario 2) since deal cards use the same `<AffiliateLink>` primitive `AffiliateClickTracker` already listens for — no changes needed to `lib/analytics.ts` or the tracker component.
