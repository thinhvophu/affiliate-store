# Feature Specification: Launch Content Remediation

**ID:** `F0013`
**Epic/Module:** Content Operations — Pre-Launch Data Quality
**Status:** Approved

---

## 1. Business Objective

A production-readiness audit (2026-08-12) found the codebase launch-ready but the **content data** not. The site builds clean (33 static pages, 121 tests passing, every SEO chokepoint in place), yet what those pages render is broken or thin in five specific, measurable ways: 5 of 8 blog posts point their `coverImage` at a **1×1 pixel, 332-byte placeholder JPEG** left over from the mock-product cleanup (commits `cf12dbe`, `7b22ee8`) — which the build cannot detect, so it ships a blank hero, a blank listing card, and a blank `og:image` declared as `1200×630`; 5 of 8 posts are **under 70 words** (the audit said 100–118; see US00134 for why the counters differ), far below the depth needed to rank for buyer-intent keywords and the single most common reason Google AdSense rejects an affiliate site — and re-measuring showed the other 3 posts run only 237–514 words, so **all 8** need rewriting, not 5; the catalog holds **10 products against a launch minimum of 12** (`docs/spec.md` §9) with names and descriptions copied verbatim from Shopee listing titles; **2 of 5 registered categories have zero products** yet are still emitted into `sitemap.xml` and linked from the homepage; and the canonical base URL is still `https://example.com`, which would poison every canonical, OG tag, JSON-LD URL and sitemap entry on day one.

This feature is a **bounded data-remediation pass** — no new routes, no new components, no architectural change. It fixes the five findings, and adds the build-time guards that stop each class of defect from silently reaching production again.

**Decision (2026-08-25, product owner):** superseding the 2026-08-22 "rewrite all 8" decision below — the 5 thin posts (`chuot-gaming-cho-fps`, `chuot-gaming-khong-day-tot-nhat`, `chuot-gaming-rgb-dep`, `tai-nghe-gaming-kiem-tra`, `ban-phim-gaming-co-switch-tot-nhat`) are **deleted outright** rather than rewritten, along with their orphan placeholder cover images (`logitech-g102-lightsync.jpg`, `keychron-k2-v2.jpg`), which satisfies US00133 Scenario 1's "orphan files deleted" clause by removing the only files that referenced them. The other 3 originally-audited posts (`ban-phim-co-cho-nguoi-moi`, `top-5-chuot-gaming-gia-re`, `danh-gia-chuot-gaming-g305-deathadder`) are unaffected by this decision — they stay in scope for US00134's depth work. US00134's 800-word floor and no-exemption guard (Scenario 4) now apply only to posts that exist in `content/posts/`; a deleted post is out of the guard's scope, not a grandfathered exception to it.

## 2. Scope

### In Scope

Listed in dependency order (US00131 → US00135):

- Growing the catalog past the launch minimum and cleaning the editorial quality of the existing scraped fixtures (`name`, `description`, `slug`).
- Resolving the two zero-product categories (`man-hinh-gaming`, `ghe-gaming`) so no empty category page is reachable, linked, or indexed.
- Deleting the 5 posts carrying the degenerate 1×1 placeholder cover images, and the two orphan placeholder files themselves (`logitech-g102-lightsync.jpg`, `keychron-k2-v2.jpg` — superseded by the 2026-08-25 decision above), plus a **build-time assertion** in the post loader that any remaining/future post's `coverImage` resolves to a real, non-degenerate file — the same "fail `next build` loudly, name the offending slug" pattern already used by `assertAffiliateUrl` / `assertCategoryRegistered`.
- Rewriting the **3 remaining originally-audited posts** to publish-grade depth, each carrying at least one `<ProductCard slug="…" />` affiliate embed. (The 2026-08-22 decision had widened this to all 8; the 2026-08-25 decision removed the 5 thin posts from the catalog instead of rewriting them, narrowing US00134's scope back down.)
- Verifying `NEXT_PUBLIC_SITE_URL` end-to-end: the Vercel Production value, the deployed `sitemap.xml` / `robots.txt` / canonical / `og:url` / JSON-LD output, and the placeholder value baked into `.github/workflows/ci.yml`.

### Out of Scope

- **Any change to `app/`, `components/`, or the route map** — except the post-loader guard in `lib/posts.ts` and, if the chosen resolution for US00132 is deferral, the category registry in `lib/categories.ts`.
- Analytics, CI, formatting, and Search Console work — those are **F0014**.
- AdSense integration itself (spec §2 marks it P1, and no feature owns it yet). This feature only removes the content-quality reasons an AdSense application would be rejected.
- Automating prose generation. `F0012`'s `scaffold:post` produces stubs; a human writes the article body (unchanged rule).
- Ongoing editorial cadence (spec §7.2 targets 4–8 posts/month). This feature brings the _existing_ content to launch quality once.
- Redirects for changed product URLs — the site is not yet indexed under the production domain, so slug changes in US00131 are free.

## 3. Process Flow

Stories are numbered in **dependency order** — each one consumes the output of the ones before it. The ordering rule is *what a story changes for the stories after it*: US00131 settles product slugs and image filenames, US00132 settles which categories exist, US00133 settles covers, US00134 consumes all three, and US00135 freezes the public URL space last.

1. **US00131 — catalog cleanup & growth.** Clean the 10 existing fixtures (`name` / `description` / `slug`) and ingest enough products to clear the launch minimum, via the existing `npm run ingest:products` pipeline (F0012). First, because renaming a product's `slug` also renames its staged image under `public/static/images/products/`, which is exactly what US00133's covers and US00134's `<ProductCard slug>` embeds point at.
2. **US00132 — zero-product categories.** Resolve `man-hinh-gaming` / `ghe-gaming` once the catalog is final: whether they can be stocked or must be deferred out of the registry is only answerable after US00131 decides what got ingested — and the ≥3-products-per-category guard this story introduces can only pass once US00131 has grown the under-stocked categories.
3. **US00133 — cover images & build guard.** The 5 posts with broken covers are deleted (2026-08-25 decision), which also removes the orphan placeholders; land the post-loader guard so a re-break fails the build going forward.
4. **US00134 — rewrite thin posts.** Now scoped to the 3 remaining originally-audited posts. After US00133, so each rewritten post's `<ProductCard>` embeds reference final product slugs (US00131), sit in a category that still exists (US00132), and carry a cover the guard accepts (US00133).
5. **US00135 — canonical domain.** Last, and this is a **correction to the feature's original sequencing**: putting the domain first looked right (nothing verifies while the base URL is `https://example.com`), but it inverts the real dependency. Setting the production domain starts Search Console crawling, and from that moment US00131's product-slug rewrites and US00132's removed category URLs would need redirects an SSG-only site cannot serve. The domain must therefore be frozen *after* the URL space is final, not before.
   - **Exception:** this story's Half A — making the `.env.example` / CI placeholders unambiguous and building `scripts/verify-canonical.ts` — has no dependencies and may be built at any point in the feature, including first. Only Half B (set the Vercel Production value → redeploy → verify) is order-sensitive.
6. Run `npm run build` + `npm test` locally; review the rendered pages in a browser (post hero, blog listing cards, category pages, homepage) before pushing to `main`.

## 4. User Stories & Acceptance Criteria

### US00131: Clear the catalog launch minimum & clean scraped fixtures

**As a** site visitor,
**I want to** product pages whose title, URL and description read like an editorial storefront,
**So that** the site does not look like a scraped mirror of Shopee search results.

**Context:** 10 products against the `docs/spec.md` §9 minimum of 12, distributed 6 chuột / 3 tai nghe / 1 bàn phím. Names are raw Shopee listing titles (e.g. `"Chuột Gaming Razer Viper Mini - Nhẹ, nhạy, chuẩn xác. Lựa chọn hoàn hảo cho game thủ!"`), which flow straight into `<h1>`, `<title>` and breadcrumbs; derived slugs run 95–98 characters; `description` values are verbatim Shopee copy still carrying the `"Mô tả chi tiết:\n"` prefix, which is duplicate content against the source listing.

**Acceptance Criteria:**

- **Scenario 1:** Catalog clears the launch minimum with sane distribution
  - `Given` `content/products/`
  - `When` the fixtures are counted
  - `Then` there are at least 12 products, and no category that ships to production has fewer than 3

- **Scenario 2:** Product names are editorial, not scraped titles
  - `Given` any product fixture
  - `When` its `name` is inspected
  - `Then` it is a clean product name (brand + model + key qualifier), free of marketing punctuation, exclamation marks, seller boilerplate (`"chính hãng"`, `"giá rẻ"`, `"BH 24 tháng"`), and at most ~70 characters so it renders as a usable `<title>` and `<h1>`

- **Scenario 3:** Slugs are short and stable
  - `Given` any product fixture
  - `When` its `slug` is inspected
  - `Then` it is at most 60 characters, and any slug change is propagated in the same change to every `<ProductCard slug>` embed, every `coverImage` referencing that product's staged image, and the staged image filenames under `public/static/images/products/`

- **Scenario 4:** Descriptions are original, not duplicated from Shopee
  - `Given` any product fixture
  - `When` its `description` is inspected
  - `Then` it is original Vietnamese editorial copy with no `"Mô tả chi tiết:"` prefix and no verbatim block copied from the Shopee listing

- **Scenario 5:** Affiliate links actually work
  - `Given` every product's `affiliateUrl`
  - `When` each is opened
  - `Then` it resolves to the correct live Shopee product page (per the `docs/spec.md` §9 launch checklist item), and any dead link is fixed or its product removed before launch

### US00132: Resolve zero-product categories

**As a** search crawler,
**I want to** never be pointed at a category page with no products on it,
**So that** the site does not accumulate thin / soft-404 pages at launch.

**Context:** `man-hinh-gaming` and `ghe-gaming` are registered in `lib/categories.ts` with zero products. All 5 registered slugs are emitted into `sitemap.xml` (verified in the build output), pre-rendered by `app/danh-muc/[category]/page.tsx`'s `generateStaticParams`, linked from `components/CategoryHighlights.tsx` on the homepage, and listed in `components/CategoryNav.tsx` on sibling category pages.

**Acceptance Criteria:**

- **Scenario 1:** No empty category ships
  - `Given` the production build
  - `When` every URL in `sitemap.xml` under `/danh-muc/` is rendered
  - `Then` each one displays at least 3 products — either because products were ingested into it, or because the category was removed from the registry until it has inventory

- **Scenario 2:** Deferring a category removes it everywhere at once
  - `Given` the decision to defer a category rather than stock it
  - `When` it is removed from `lib/categories.ts`
  - `Then` it disappears from `sitemap.xml`, `generateStaticParams`, `CategoryHighlights` and `CategoryNav` simultaneously — because all four already read the same registry, no per-surface edit is required, and no dangling internal link remains

- **Scenario 3:** Empty categories cannot silently reappear
  - `Given` a registered category with zero products
  - `When` `npm run build` (or the test suite) runs
  - `Then` it fails naming the empty category slug, so registering a category ahead of its inventory is caught before deploy rather than after indexing

### US00133: Remove degenerate placeholder cover images & guard against regression

**As a** site visitor arriving from a shared link,
**I want to** see a real cover image on every blog post,
**So that** the post does not look broken on the listing, the article header, or a social share card.

**Context (audit findings):** `public/static/images/products/logitech-g102-lightsync.jpg` and `keychron-k2-v2.jpg` were both 332-byte, 1×1, single-component baseline JPEGs. Five posts referenced them: `chuot-gaming-cho-fps.mdx`, `chuot-gaming-khong-day-tot-nhat.mdx`, `chuot-gaming-rgb-dep.mdx`, `tai-nghe-gaming-kiem-tra.mdx` (all four → `logitech-g102-lightsync.jpg`) and `ban-phim-gaming-co-switch-tot-nhat.mdx` (→ `keychron-k2-v2.jpg`). Neither file corresponded to a product still in the catalog. **Resolved (2026-08-25):** rather than sourcing 5 replacement covers, the 5 referencing posts were deleted outright, which took both orphan image files with them (`git rm` on the fixtures made the images unreferenced-and-removed in the same change, not a separate cleanup pass).

**Acceptance Criteria:**

- **Scenario 1:** Every remaining post cover resolves to a real image
  - `Given` the posts in `content/posts/` after the 2026-08-25 deletion
  - `When` the site is built
  - `Then` every post's `coverImage` points to a file that exists under `public/`, is a valid image, and is at least 600px on its shorter side — no post references `logitech-g102-lightsync.jpg` or `keychron-k2-v2.jpg`, and both files are absent from the repository

- **Scenario 2:** Cover images are not reused across posts
  - `Given` the posts remaining after the 2026-08-25 deletion
  - `When` their `coverImage` values are compared
  - `Then` no two posts share the same `coverImage` path, so listing cards and social shares are visually distinct

- **Scenario 3:** A broken or missing cover fails the build, not production
  - `Given` a post whose `coverImage` points to a nonexistent path, or to a file below the minimum-dimension threshold
  - `When` `npm run build` runs
  - `Then` the build exits non-zero naming the offending post slug and the offending path — mirroring how `assertAffiliateUrl` / `assertCategoryRegistered` already fail the build for bad product data

- **Scenario 4:** Social preview metadata matches reality
  - `Given` any post page in the production build output
  - `When` its `og:image` / `og:image:width` / `og:image:height` tags are inspected
  - `Then` the referenced image actually exists at usable dimensions (the audit found a 1×1 file advertised as `1200×630`)

### US00134: Rewrite thin posts to publish-grade depth

**As a** reader searching a Vietnamese buyer-intent keyword,
**I want to** land on an article that actually answers the question,
**So that** the page earns its ranking and the site clears Google's and AdSense's content-quality bar.

**Context:** word counts at audit time, measured with `countWords()` from `lib/format.ts` — the project's own counter, the one already backing `readingTimeVi()`:

| Post | words |
| --- | --- |
| `chuot-gaming-cho-fps` | 53 |
| `chuot-gaming-khong-day-tot-nhat` | 56 |
| `chuot-gaming-rgb-dep` | 57 |
| `tai-nghe-gaming-kiem-tra` | 58 |
| `ban-phim-gaming-co-switch-tot-nhat` | 64 |
| `ban-phim-co-cho-nguoi-moi` | 237 |
| `top-5-chuot-gaming-gia-re` | 288 |
| `danh-gia-chuot-gaming-g305-deathadder` | 514 |

The readiness audit reported 100–118 words for the thin five and 314 / 404 / 635 for the other three; those figures came from a different counter (whole-file, including frontmatter and JSX). The ranking is identical, but **the floor is only meaningful once the counter is pinned** — hence the counter is named normatively in Scenario 1.

Two consequences followed at audit time. First, **no post cleared 800 words** — not even the three previously called "acceptable". Second, only 4 `<ProductCard>` embeds existed across all 8 posts, so 4 posts had no monetization path at all.

**Decision (2026-08-22, product owner):** the depth floor applies to **all 8 posts** — every post is rewritten, and the three longer ones are expanded rather than grandfathered. Rationale: Scenario 4 is written for *any* post, §5 forbids a silently lowered threshold, and a guard carrying three permanent exceptions is a guard nobody trusts. A 237-word post is exactly the thin content an AdSense review rejects, so exempting it would defeat the feature's purpose. The considered alternative — enforcing 800 on the five named posts and adding a documented `LEGACY_SHORT_POSTS` exemption set — was **rejected**. Cost accepted: 8 articles, not 5.

**Decision (2026-08-25, product owner):** superseding the above for the 5 thin posts specifically (see the Business Objective section) — the five rows at the top of the table (`chuot-gaming-cho-fps` through `ban-phim-gaming-co-switch-tot-nhat`) were **deleted**, not rewritten. US00134's remaining scope is the 3 previously-"acceptable" posts (`ban-phim-co-cho-nguoi-moi`, `top-5-chuot-gaming-gia-re`, `danh-gia-chuot-gaming-g305-deathadder`), which the "no grandfathering" rationale from 2026-08-22 still governs in full — they are rewritten to the 800-word floor, not exempted.

**Acceptance Criteria:**

- **Scenario 1:** Every published post meets a depth floor
  - `Given` the posts in `content/posts/` remaining after the 2026-08-25 deletion — the 3 previously considered acceptable
  - `When` they are rewritten
  - `Then` each is at least 800 words of Vietnamese prose as counted by `countWords()` in `lib/format.ts` (the single counter, shared with read-time), structured with `h2`/`h3` sections (so the F0006 table of contents has something to render), and reads as a genuine buying guide / comparison / best-of piece per `docs/spec.md` §7.3 — not padded filler

- **Scenario 2:** Every post has a monetization path
  - `Given` any post in `content/posts/`
  - `When` its body is inspected
  - `Then` it embeds at least one `<ProductCard slug="…" />` whose slug resolves to a product in `content/products/` (a bad slug already fails the build via `<MdxProductCard>`)

- **Scenario 3:** Frontmatter is complete and non-placeholder
  - `Given` any post after rewriting
  - `When` its frontmatter is inspected
  - `Then` `title`, `summary`, `publishedAt`, `category`, `tags`, `coverImage` are all populated with real values — no `TODO:` placeholder from `scaffold:post` survives, `summary` is a genuine meta description (not a truncated first line), and `tags` is non-empty

- **Scenario 4:** Depth floor is enforced, not just intended
  - `Given` a post below the word-count floor
  - `When` the test suite runs
  - `Then` it fails naming the post slug and its word count, so a future stub post cannot be published by accident
  - `And` the check covers **every** post with no exemption list — per the 2026-08-22 decision above, no post is grandfathered

### US00135: Canonical production domain verified end-to-end

**As a** site owner,
**I want to** every canonical URL, OG tag, JSON-LD URL and sitemap entry to carry the real production domain, and the site's own name to match it,
**So that** Google indexes the live site rather than `https://example.com`, and the brand shown to users and in metadata is consistent with the registered domain.

**Context:** `.env.local` and the `build` job in `.github/workflows/ci.yml` both set `NEXT_PUBLIC_SITE_URL=https://example.com`; the locally-built `sitemap.xml` emits `<loc>https://example.com/</loc>`. The value configured on Vercel Production is not verifiable from the repository and must be checked directly. **The production domain is now registered: `muagear.com`** (confirmed with the user, 2026-09-02). Separately, `lib/site.ts`'s `SITE_NAME` constant and `package.json`'s `"name"` field both still read `"aff-store"` — a placeholder name predating the domain purchase — and were folded into this story's scope (2026-09-02 decision) rather than filed separately, since both are "things that need to change because of the real domain."

**Acceptance Criteria:**

- **Scenario 1:** Production environment carries the real domain
  - `Given` the Vercel project's Production environment
  - `When` `NEXT_PUBLIC_SITE_URL` is inspected
  - `Then` it is `https://muagear.com` (scheme + host, no trailing slash), and a fresh Production deploy has been triggered so the value is baked into the static output

- **Scenario 2:** Deployed output carries no placeholder domain
  - `Given` the deployed production site
  - `When` `/sitemap.xml`, `/robots.txt`, and the `<link rel="canonical">` / `og:url` / JSON-LD `url` fields of one product page, one post page and one category page are fetched
  - `Then` every absolute URL uses `muagear.com` and `example.com` appears nowhere in the deployed output

- **Scenario 3:** Local and CI placeholders are unambiguous
  - `Given` `.env.example` and the CI `build` job
  - `When` a contributor reads them
  - `Then` the placeholder is clearly a placeholder and CI still builds without needing a real domain — CI is a build smoke test, not a canonical-URL source

- **Scenario 4:** Site branding matches the registered domain
  - `Given` `lib/site.ts`'s `SITE_NAME` constant and `package.json`'s `"name"` field
  - `When` either is inspected, or any surface that renders `SITE_NAME` (Header, Footer, root `<title>` template, JSON-LD `Organization`/publisher name) is viewed
  - `Then` `SITE_NAME` reads `"MuaGear"` (not `"aff-store"`) and `package.json`'s `"name"` is updated to match (kebab-case package identifier, e.g. `"muagear"`), with no leftover `"aff-store"` string in either file

## 5. Edge Cases & Error Handling

- **A replacement cover image does not exist for a post's topic:** reuse the post's _own_ primary embedded product image (the `scaffold:post` convention from US00126), never another post's cover — Scenario 2 of US00133 forbids sharing.
- **Deleting an orphan image that is still referenced:** the US00133 build-time guard is the backstop — deletion and reference-update must land in the same change or the build fails loudly.
- **A cleaned product slug collides with an existing one:** the F0012 dedupe rules (`scripts/ingest/dedupe.ts`, keyed `affiliateUrl` first, slug second) still apply; disambiguate rather than overwrite.
- **Rewriting a post changes its topic enough that its `category` should change:** allowed, but the new category must be registered and non-empty after US00132 — otherwise `lib/posts.ts`'s `assertCategoryRegistered` fails the build.
- **A `<ProductCard>` embed references a product later removed for a dead affiliate link (US00131 Scenario 5):** `<MdxProductCard>` already throws a slug-named build error; fix the post in the same change.
- **The production domain is not yet registered when this feature starts:** nothing blocks — this is precisely why US00135 sits last in the dependency order rather than first. Its Half A (placeholder hygiene + the `verify:canonical` script) has no predecessors and may be built at any point, including first; only Half B (set the Vercel Production value → redeploy → verify the deployed output) waits for the domain, and it must not run until US00131's slug rewrites and US00132's category removals have merged.
- **Word-count floor vs. a legitimately short post type:** the floor applies to published buyer-intent content, and as of the 2026-08-22 decision it applies with no exemption list to every post that remains published (as of 2026-08-25, the 3 previously-"acceptable" posts). If a genuinely short format is wanted later, the enforcement in US00134 Scenario 4 needs an explicit, documented exemption added deliberately — not a silently lowered threshold, and not a quiet re-grandfathering of the posts this decision covers. Deleting a thin post is a distinct, explicitly-decided path (2026-08-25) — not a precedent for silently dropping a future post to dodge the floor.

## 6. Technical Considerations

- **This feature is data + guards, not architecture.** The only production-code changes expected are (a) the cover-image assertion in `lib/posts.ts`, and (b) possibly removing entries from `lib/categories.ts`. No new route, no new component, no change to the route map or the `Codebase structure` map in `CLAUDE.md` beyond noting the new guard.
- **Guards follow the established build-time-assert pattern.** `lib/products.ts` already calls `assertAffiliateUrl` + `assertCategoryRegistered` and fails `next build` naming the offending slug. The cover-image check belongs in `lib/posts.ts` in the same style — reading from `public/` with `fs` at build time is already how content loading works, and `next build` is the gate every deploy passes through. Checks that need no filesystem access (word count, duplicate covers, empty categories) may live in the Vitest suite instead — but see F0014/US00143: **the test suite is not currently run in CI**, so a test-only guard is not yet a real gate.
- **Slug changes are free right now and will not be later — this is the dependency that sets the whole story order.** The site is not indexed under the production domain yet, so US00131's slug cleanup and US00132's category removals need no redirects. Once US00135's Half B lands and Search Console starts crawling, the same changes would require a redirect strategy the project has no mechanism for (SSG-only, no middleware). Every URL-changing story therefore precedes the domain freeze, not the other way round.
- **Product images are already staged locally** (US00123) — cleaning a slug means renaming files under `public/static/images/products/` and updating the fixture's `images` array. `scripts/ingest/writer.ts` refuses to write a remote URL, so a hand-edit that pastes a Shopee CDN URL fails loudly.
- **Growing the catalog should use the existing pipeline** (`npm run ingest:products`, F0012) rather than hand-authored JSON — it enforces the affiliate host allow-list, category registration, local image staging and dedupe by construction. Note the known F0012 limitation: the scrape source currently yields no `brand`/`specs`, so `--source=file` with a curated list is the practical path until the scraper is updated upstream.
- **Verification is visual, not just structural.** Per the project's UI rule, the post hero, blog listing cards, category pages and homepage must be checked in a browser before this feature is considered done — a passing build says nothing about whether an image _looks_ right, which is exactly how the 1×1 covers shipped.
- **Relationship to AdSense:** thin content is the most common AdSense rejection reason, so US00131 + US00134 are prerequisites for any future AdSense application, but the integration itself is unowned by any feature today.
