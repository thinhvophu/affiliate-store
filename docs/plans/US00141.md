## 0. Current state (verified 2026-09-03)

```
$ npx vitest run
Test Files  22 passed (22)
     Tests  186 passed (186)

```

The spec quotes **121 tests across 15 files** (2026-08-12 audit). The suite has grown to **186 tests across 22 files** — US00131/132/133/134/135 and `sync-content-queue` all added tests. The story's premise is unchanged and stronger: more guards, still zero CI enforcement.

`.github/workflows/ci.yml` runs exactly three jobs — `typecheck`, `lint`, `build` — each with the identical shape:

```yaml
  <name>:
    name: <name>
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version-file: ".nvmrc"
          cache: "npm"
      - run: npm ci
      - run: npm run <name>
```

`build` additionally sets `env: NEXT_PUBLIC_SITE_URL: https://example.com` with a comment explaining it is a smoke test (US00135).

`package.json` already exposes `"test": "vitest run"`. `vitest.config.ts` sets `environment: "node"` and injects `NEXT_PUBLIC_SITE_URL: "https://example.com"` **inside the config**, so the `test` job needs **no** `env:` block — this is the one meaningful difference from the `build` job and is worth not copying by accident.

Runtime is sub-second; the job cost is entirely `npm ci`.

## 1. Scope

Strictly: add a fourth job named `test` to `.github/workflows/ci.yml` that runs `npm test`, matching the existing job shape, running in parallel with the other three.

**Out of scope:**

- Job consolidation / shared `npm ci` caching. Spec §5 explicitly accepts the duplicated install cost at this repo size: *"if it becomes slow, the fix is job consolidation, not dropping the gates."*
- Coverage reporting, test sharding, matrix over Node versions.
- Adding, changing or fixing any test. If the suite is red at implementation time, that is a separate bug fix, not this story.
- Branch-protection rules on GitHub (a repository setting, not a file) — see §5.

## 3. Target change

Append after the `lint` job (alphabetical-ish grouping is not used; append before `build` so the two "fast" jobs sit together, or after `build` — either is fine, pick **after `lint`, before `build`** so cheap jobs precede the expensive one for reader scanning):

```yaml
  test:
    name: test
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version-file: ".nvmrc"
          cache: "npm"
      - run: npm ci
      - run: npm test
```

Notes on deliberate choices:

- **`npm test`, not `npm run test`.** `test` is an npm lifecycle script; both work. `npm test` is the idiomatic form and reads consistently with the other jobs' `npm run <name>` for non-lifecycle scripts.
- **No `env:` block.** `vitest.config.ts` already supplies `NEXT_PUBLIC_SITE_URL`. Adding a workflow-level env var here would create a second, silently-diverging source for the same value.
- **No `if:` condition, no `needs:`.** Scenario 3 requires it run *in parallel*, not serially. GitHub Actions runs jobs in parallel by default when no `needs:` is declared — so the requirement is met by omission, and adding `needs:` would violate it.
- The existing `concurrency` block (`cancel-in-progress: true`) applies workflow-wide and needs no change.

## 4. Step-by-step execution order

1. Branch `feat/US00141-ci-test-job` off `main`.
2. Edit `.github/workflows/ci.yml` — insert the `test` job per §3.
3. Locally confirm green: `npm test` → 186/186 pass.
4. Lint the YAML by eye against the three existing jobs — key order, indentation (2 spaces), quoted `".nvmrc"` / `"npm"` strings must match character-for-character (Scenario 3 is literally a diff-comparison criterion).
5. Push, open PR. **Confirm on the PR that four checks now appear** and `test` is green (Scenario 1).
6. **Scenario 2 — prove it goes red.** On a throwaway branch off this one, break one assertion (e.g. flip an expected value in `lib/format.test.ts`), push, open a draft PR, screenshot/record the red `test` check, then **delete the branch and the draft PR**. Paste the evidence into the US00141 PR description. Do **not** merge the broken commit, and do not leave the scratch branch behind.
7. Merge the US00141 PR.

## 5. Post-merge operator step (not code)

Scenario 2's phrase *"the PR is not mergeable"* is only literally true once `test` is a **required** status check. That is a GitHub repository setting, not a file in this repo:

> Settings → Branches → branch protection rule for `main` → *Require status checks to pass before merging* → add `test` (and, while there, `typecheck`, `lint`, `build`, and later `format` from US00142).

Record in the PR whether branch protection was enabled. If the repo has no protection rule at all today, the honest statement is "the job runs and goes red; blocking the merge requires the branch-protection rule above" — do not claim the merge is blocked if nothing enforces it.

## 7. Risks

- **Suite red on `main` at implementation time.** Check `npm test` before branching. If red, fix (or file) that first — landing a job that is instantly red on `main` is worse than not landing it.
- **`.nvmrc` says `22`, `engines` says `>=22.11.0`.** `setup-node` resolves `22` to the latest 22.x, which satisfies the engine. Already true for three jobs; no new risk.
- **Doubling `npm ci` runs (3 → 4).** Accepted by spec §5.
