**Status:** Approved
**Feature:** F0015 — Weekly Deal Roundup Content
**Spec ref:** `docs/specs/F0015.md` § US00154
**Predecessors:** **US00151, US00152, US00153 (all hard)** — this story sequences them and adds the one piece none of them can contain: the MCP call.

## 0. Why the entry point is a slash command, not an npm script

Spec §3 step 2 has the script calling `mcp__shopee-affiliate__scrape_products`. It cannot: MCP tools are exposed to the Claude Code client, not to a `tsx` process (see US00151 § 0, decision **D1**). So the "single command" of Scenario 1 is a **slash command** — the only actor that can both call the MCP tool and shell out to the CLIs.

This is not a workaround invented for F0015; it is the established shape of every recurring content operation in this repo. `.claude/commands/scrape-ingest.md` § 3 calls the same MCP tool and then shells into `npm run ingest:products`. `.claude/commands/write-post.md` shells into `npm run scaffold:post` and then writes the prose itself. **`/deal-roundup` is the two combined**, which is exactly what spec §3's seven-step flow describes — and why Scenario 1's _"matching the existing `/scrape-ingest` / `/write-post` convention"_ names those two commands specifically.

**Two-tier publishing, consistent with the repo's rules.** The command _file_ is code and ships through a normal feature branch + PR (`CLAUDE.md`: implement a story on a `feat/*` branch, PR is the review gate). Every weekly _run_ of the command thereafter is a content operation and pushes straight to `main`, like `/scrape-ingest` and `/write-post` (`CLAUDE.md` § Working conventions: _"Publishing flow: add file → push to `main` → Vercel rebuilds"_).

## 1. Scope

1. `.claude/commands/deal-roundup.md` — the entry point.

## 3. Design — `.claude/commands/deal-roundup.md`

Argument shape (everything but the category optional):

```
/deal-roundup <category-slug> [--query="<từ khoá>"] [--top=5]
```

### 3.1 Resolve the category

First whitespace-separated token. **If missing, do not guess** — read `lib/categories.ts`, count each registered category's products, posts and _existing roundups_ (`content/deals/*.json`), and present an `AskUserQuestion`. Lifted from `/write-post` § 1, which exists because guessing a category is the one mistake that silently produces content for the wrong URL. Unregistered category ⇒ stop, listing the registered ones.

### 3.2 Resolve the keyword

`--query` if given. Otherwise the category's **registered display name** from `lib/categories.ts`, mirroring `/scrape-ingest` § 2's name-matching rule (exact, trimmed, **never fuzzy**).

**One variable, both uses.** The same resolved string is passed to the MCP call _and_ to `--query`. This is the mitigation for US00151 R3: the snapshot groups deals by the exact keyword the tool was called with, so any divergence between the two silently yields an empty roundup.

### 3.3 Scrape

Call `mcp__shopee-affiliate__scrape_products({ keywords: [keyword], top_n: <top ?? 5> })` **once**. It writes `data/deals/<today>.json` itself — the command never writes that file, and the CLI only reads it.

### 3.4 Generate (dry run, then real)

```bash
npm run generate:deal-post -- --category=<slug> --query="<keyword>" --top=<n> --dry-run
npm run generate:deal-post -- --category=<slug> --query="<keyword>" --top=<n>
```

Print both summaries. Three outcomes to read, not one:

- **Zero usable deals** ⇒ exit 0 having written nothing. **Stop here.** Report it plainly, do not commit, and state that the prior week's roundup deliberately remains "tuần này"-framed (spec §5, first bullet). This is a normal weekly outcome, not a failure.
- **Shortfall** (`requested 5, usable 3`) ⇒ proceed with what came back. Never re-run with a padded `--top` to hit a round number, and never fabricate an entry (US00151 Scenario 3).
- **Dropped deals** ⇒ mention them in the report; the roundup is still valid (US00151 Scenario 2).

The real run also supersedes the prior week's post (US00153), _after_ writing the current one.

### 3.5 Write the prose

Edit the generated `.mdx` (`Edit`/`Write`, never the CLI). Replace every `{/* TODO … */}` with real Vietnamese copy:

- An intro under the first `h2` framing the week's picks.
- A short, honest paragraph per deal under its `h3`, grounded in the sidecar's own numbers (`content/deals/<slug>.json`) — price, discount, rating, sold count — plus a `WebSearch` per distinct brand+model where one is identifiable, exactly as `/write-post` § 4 does.
- A closing "Lưu ý khi săn deal" section: stock/variant caveats, checking the seller, and that the price shown is the price at publish time.
- **≥800 words** (`MIN_POST_WORDS`), no `TODO` left anywhere.

Four things must survive untouched: every `<DealCard id>` embed (do not add, remove or reorder), the `{/* roundup-lead:… */}` markers (US00153 depends on them and **throws** if they are gone), `publishedAt`/`category`/`coverImage`, and the "tuần này" framing in `title` and the lead.

`summary` and `tags` may be refined — the generator's are real, not placeholders, but a human sentence is usually better. Keep `summary` in 50–160 chars.

### 3.6 Verify

```bash
npm run typecheck && npm run lint && npm run test && npm run build
```

All must exit 0. `npm test` is where the depth floor, the embed count, the cover-image floor and the duplicate-cover check actually bite — and thanks to **US00141** the same suite gates CI.

Then the browser check per the project's UI rule: `npm run dev`, open `/bai-viet/<slug>/`, screenshot, console clean. Confirm the deal cards, both disclosures (affiliate + price-change), TOC, breadcrumbs — **and** open the superseded post to confirm its H1 and first paragraph now name its own date. Revert `next-env.d.ts` afterwards.

**If anything fails: stop before commit.** Leave the working tree as-is. This is Scenario 2 — the new post _and_ the rewritten prior post are both sitting uncommitted, so the operator can fix and retry or `git checkout` both away cleanly.

### 3.7 Commit and push

`git status --porcelain` should show exactly:

```
content/posts/deal-<category>-<date>.mdx        (new)
content/posts/deal-<category>-<prior-date>.mdx  (modified — the superseded post)
content/deals/deal-<category>-<date>.json       (new)
public/static/images/deals/deal-<category>-<date>-*.{jpg,png,webp}  (new)
data/deals/<today>.json                          (new — the audit trail)
```

Stage exactly those paths, nothing else. Commit:

```
content: weekly <category> deal roundup (<date>)

<n> deals · superseded <prior-slug>

Co-Authored-By: Claude Opus 5 <noreply@anthropic.com>
```

Then `git push origin main`, and report the hash plus the Vercel auto-deploy reminder.

### 3.8 The ordering _is_ the atomicity guarantee

```
resolve → scrape → generate (0 deals? stop, nothing written, nothing superseded)
        → stage images (all-or-nothing, before any post is written)
        → write current post + sidecar
        → supersede prior post          ← only after the current one exists
        → write prose
        → build + browser verify        ← last gate before anything leaves the machine
        → commit → push
```

Scenario 2 asks that a failed run never leave _"the prior post silently relabeled while no current post exists."_ That is structurally impossible here: supersession is the last write and is strictly downstream of the current post's creation, and nothing is pushed until the build passes. Every intermediate failure leaves a plain, inspectable working tree.

### 3.9 Rules section (mirroring the existing commands' tone)

- Never fabricate a deal, a price, a rating or a sold count — the sidecar and the search results are the only sources.
- Never hand-edit `content/deals/*.json`; it is CLI output. A wrong deal means re-running, not patching.
- Never remove, reorder or invent `<DealCard>` embeds beyond what the generator wrote.
- Never delete the `{/* roundup-lead:… */}` markers.
- Never commit outside the five paths in §3.7.
- Never push to any branch other than `main` — this command has no feature-branch/PR step by design.
- Never skip `npm run build` or the browser check.
- If the category is ambiguous or unregistered, ask or stop — never guess.
- Zero qualifying deals is a valid outcome. Report it and stop; do not widen `--query` or drop `--top` to manufacture a post.

## 6. Risks & edge cases

- **R1 — The command drifts from the CLIs.** A prose document restating flags will rot as the scripts change. Mitigation: the command shells out and _prints the CLI's own summaries_ rather than re-deriving anything, and every threshold (`--top` bounds, the 800-word floor, the cover floor) is enforced in code with a test, not in the markdown.
- **R2 — Operator reruns with a different `--query` against the same day's snapshot.** The group won't match and the roundup comes back empty, looking like "no deals this week". Mitigated by §3.2's one-variable rule and by US00151's summary echoing both the snapshot path and the keyword.
- **R3 — Prose quality drifting toward a template.** The failure mode D8 was chosen to avoid, reappearing by habit. The rules in §3.9 plus grounding every claim in the sidecar or a search result are the guard; `MIN_POST_WORDS` catches length, not sameness, and no test can catch sameness — this one rests on review.
- **R4 — Pushing straight to `main`.** Deliberate and consistent with `/scrape-ingest` and `/write-post`, but it means the build gate in §3.6 is the _only_ gate. Hence "never skip `npm run build`" being a rule rather than a suggestion.
- **R5 — Ad-blocked / bot-filtered scrapes returning nothing.** Indistinguishable from a genuinely empty week at the command level. Both are reported as "0 usable deals, nothing written"; the summary's snapshot path lets the operator open the file and tell the two apart.
- **R6 — Scheduling pressure.** The obvious next step is a cron job, and spec §2 defers it explicitly _"once the manual flow is proven."_ Proving it means several weeks of real runs — automating before that would bake in whatever this story got wrong.
