# Implementation Plan — US00134: Rewrite thin posts to publish-grade depth

**Status:** Approved
**Feature:** F0013 — Launch Content Remediation
**Spec ref:** `docs/specs/F0013.md` § US00134 · `docs/spec.md` §7.3, §9
**Predecessors:** US00131 (`<ProductCard slug>` embeds must reference final product slugs), US00132 (the post's `category` must still be registered), US00133 (each post must carry a cover the new build guard accepts).
**Successors:** US00135 (Half B verifies the deployed output once the content is final; it closes the feature).

---

## 1. Scope

Strictly:

1. Rewrite the 5 thin posts into genuine Vietnamese buying guides / comparisons, structured with `h2`/`h3` so the F0006 table of contents has something to render.
2. Ensure **every** post embeds ≥1 `<ProductCard slug="…" />` (4 of 8 have none today).
3. Complete/verify frontmatter on every post — real `title`, genuine meta-description `summary`, `publishedAt`, live `category`, non-empty `tags`, valid `coverImage`; no `TODO:` placeholder survives.
4. Add the **word-count floor enforcement** to the test suite, failing with the post slug and its count.

**Explicitly out of scope:**

- Automated prose generation (F0013 §2 — a human writes the article body; `scaffold:post` only makes stubs).
- New posts beyond the existing 8 (ongoing editorial cadence is out of scope; §9 wants ≥5 posts, and 8 already clears it).
- Cover images / the cover guard — **US00133**.
- Product data — **US00131**.

They rank the posts identically, so no conclusion changes, but **the floor is meaningless until the counter is fixed.** D1 below pins it to `countWords`, and every number in this plan is measured with it.

### 2.2 The consequence that needs a decision

**No post in the repo currently clears 800 words by this counter — not even the three "acceptable" ones.** Scenario 1 targets the 5 thin posts, but Scenario 4 is written generally ("Given a post below the word-count floor … it fails naming the post slug"). A global 800-word test therefore fails `ban-phim-co-cho-nguoi-moi` (237), `top-5-chuot-gaming-gia-re` (288) and `danh-gia-chuot-gaming-g305-deathadder` (514) as well. See **D2** — this is the one decision in F0013 that changes the size of the work, and it needs the user's sign-off.

### 2.3 Structural facts

- `ban-phim-co-cho-nguoi-moi` has **zero `h2`** — the TOC renders nothing for it today, so it needs restructuring regardless of length.
- A bad `<ProductCard slug>` already fails `next build` via `<MdxProductCard>`; no new guard is needed for Scenario 2's slug-resolution half.
- `lib/posts.ts::validatePostFrontmatter` already rejects empty `title`/`summary`/`publishedAt`/`category`/`coverImage` and non-array `tags` — but it accepts `"TODO: …"` and `tags: []`. Scenario 3 needs both closed.

## 3. Approved Decisions

| # | Decision | Choice | Rationale |
| --- | --- | --- | --- |
| D1 | The counter is normative | The floor is defined as `countWords()` from `lib/format.ts`, **exported** (currently module-private) and reused by the test — never a second implementation | The project's "one chokepoint" rule. Read-time and the depth floor must not disagree about what a word is. Exporting also lets `lib/format.test.ts` keep covering it. |
| D2 | **Floor applies to all 8 posts** → the 3 longer posts get expanded too (237→800+, 288→800+, 514→800+) | **Confirmed by the user 2026-08-22 — rewrite all posts** | Scenario 4 is written for *any* post, and F0013 §5 explicitly forbids "a silently lowered threshold". A guard with three grandfathered exceptions is a guard nobody trusts. Also: 237- and 288-word posts are exactly the thin content AdSense rejects, so exempting them defeats the feature's purpose. **Cost: 3 extra articles (8 total, not 5).** *Alternative if the user declines:* enforce 800 on the 5 named posts and add an explicit, commented `LEGACY_SHORT_POSTS` exemption set in the test with a dated TODO — documented, not silent, per §5. |
| D3 | Floor value | `export const MIN_POST_WORDS = 800` in `lib/format.ts`, next to the counter | Spec value. Note it is 800 *whitespace tokens*; Vietnamese tokens are syllables, so this is roughly 600–700 English-equivalent words — a sane, achievable buying-guide length, not a padding invitation. |
| D4 | Enforcement location | Vitest, in the existing `lib/posts.test.ts` created by US00133 | Scenario 4 says "when the test suite runs". A `next build` throw on prose length would block emergency content edits and is a judgement rule, not a structural one. **Caveat: CI does not run tests yet (F0014/US00143)** — until that lands, `npm test` must be run manually before every content merge. Call this out in the PR. |
| D5 | Additional frontmatter assertions in the same test | (a) no field contains `TODO`; (b) `tags.length >= 1`; (c) `summary` is 50–160 chars and is **not** a prefix of the body's first paragraph (catches "truncated first line"); (d) every post has ≥1 `<ProductCard slug=` and ≥2 `h2` headings | Scenario 3's "genuine meta description, not a truncated first line" and Scenario 1's "structured with h2/h3 so the TOC has something to render" are otherwise unenforceable good intentions. |
| D6 | Article shape (per post) | Intro (the buyer question) → `h2` selection criteria → `h2` per pick with an `h3` pros/cons breakdown and the `<ProductCard>` embed → `h2` comparison table → `h2` FAQ / "nên chọn cái nào" → close | Matches `docs/spec.md` §7.3, gives the TOC 4–6 anchors, and puts an affiliate card next to each recommendation instead of dumping them at the end. |
| D7 | Which products each post embeds | Only products in the final US00131 catalog, matching the post's category and its US00133 cover: FPS → Viper Mini + Viper V3 Pro SE; wireless → Viper V3 Pro SE + G305; RGB → G502 HERO + G402; 7.1 headsets → E-Dra EH404 + HyperX Cloud Earbuds III; switches → DAREU EK75 + the newly ingested keyboard(s) | Every embed resolves (build-enforced), each post monetises its own subject, and the lead product matches its cover image. |
| D8 | `publishedAt` on rewritten posts | Keep the original dates | Changing them would reshuffle `/bai-viet/` ordering and the sitemap for no reader benefit. The content is being fixed, not republished as new. |
| D9 | Honesty rule for the prose | Only claim specs that appear in the product fixture's `specs` (which came from the Shopee listing). No invented benchmark numbers, no fabricated hands-on testing | The site has not physically tested these products. Fabricated review claims are both an AdSense risk and simply false. Where a comparison needs a judgement, phrase it as reasoning from published specs. |
| D10 | Language & tone | Vietnamese throughout (project rule); second person, concrete price bands in `₫` via the rendered `formatVnd` values, no keyword stuffing | `docs/spec.md` §7.3 + the all-copy-is-Vietnamese working convention. |

## 5. Step-by-step execution order

1. Branch `feat/US00134` (after US00131–US00133 merge).
2. **Guard first:** export `countWords` + `MIN_POST_WORDS`; add the D4/D5 cases to `lib/posts.test.ts`. Confirm the suite fails, listing all 8 slugs with their counts — that failure list *is* the work queue.
3. Rewrite in dependency order, one post per commit (reviewable, and a bad article can be reverted alone):
   1. `chuot-gaming-cho-fps`
   2. `chuot-gaming-khong-day-tot-nhat`
   3. `chuot-gaming-rgb-dep`
   4. `tai-nghe-gaming-kiem-tra`
   5. `ban-phim-gaming-co-switch-tot-nhat`
   6. `ban-phim-co-cho-nguoi-moi` *(D2)*
   7. `top-5-chuot-gaming-gia-re` *(D2)*
   8. `danh-gia-chuot-gaming-g305-deathadder` *(D2)*

   For each: pull the real `specs` from the fixture (D9), write to the D6 shape, place embeds inline, refresh `summary` into a genuine 50–160-char meta description, top up `tags`, re-run `npm test -- lib/posts.test.ts`.
4. `npm run typecheck && npm run lint && npm test && npm run build`.
5. **Browser verification** (project UI rule): for each post — TOC renders and its anchors jump correctly (F0006/US00068 slugs), embedded `<ProductCard>`s render with images and prices, the read-time chip is sane, `AffiliateDisclosure` sits above the body, related posts populate. Then `/bai-viet/` listing (summaries fit the clamp) and one mobile-width pass.
6. Docs; PR `feat/US00134` → `main`. All F0013 **content** work is now done; only US00135's domain swap + verification remains.

## 9. Risks / open items

- **R1 — ~~D2 open~~ resolved.** The user confirmed the global floor on 2026-08-22: all 8 posts are rewritten, no exemption list. The story is 8 articles, not 5.
- **R2 — Padding to hit the number.** An 800-word floor invites filler, which is the exact failure mode the spec calls out ("not padded filler"). Mitigation: D6's fixed shape means length comes from *sections that answer real questions*; review each commit for whether a section could be deleted without losing information.
- **R3 — Fabricated claims (D9).** The most serious editorial risk. No performance number, benchmark or "we tested" claim may appear that is not derived from the fixture's `specs` or clearly framed as reasoning.
- **R4 — Test-only enforcement is not yet a CI gate** (F0014/US00143). Until the `test` job exists, a future stub post can be merged green. Flag prominently in the PR; consider sequencing US00143 soon after F0013.
- **R5 — Counter drift.** If `countWords`'s stripping rules ever change, the floor silently moves. Mitigated by exporting the single function (D1) and by `lib/format.test.ts` pinning its behaviour.
- **R6 — Eight posts is a long PR.** Mitigated by one-post-per-commit (step 3); reviewers can read commit by commit. Splitting into two PRs (the 5 required, then the 3 from D2) is acceptable if review drags.
- **R7 — Related-posts thinning.** Category counts shift as posts are rewritten but not re-categorised, so `getRelatedPosts` output is unchanged. Confirm in step 5 rather than assuming.
