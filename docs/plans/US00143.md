### D1 — Decision: hand-rolled `next/script`, **not** `@next/third-parties/google`

Spec §6 requires this choice be made after reading the docs and justified. Both are viable; `next/script` wins here:

|                     | `@next/third-parties` `<GoogleAnalytics>`                                                                                                                                                 | hand-rolled `next/script`                                                                                                                |
| ------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------- |
| Stability           | The doc states verbatim: _"`@next/third-parties` is currently an **experimental** library under active development. We recommend installing it with the **latest** or **canary** flags."_ | `next/script` is stable, already in `next`.                                                                                              |
| New dependency      | Yes                                                                                                                                                                                       | No                                                                                                                                       |
| Env gating          | Component always renders; we still need our own conditional wrapper.                                                                                                                      | Same wrapper, nothing extra.                                                                                                             |
| Client boundary     | Ships its own client component into the root layout on every page.                                                                                                                        | Two `<Script>` tags; can stay a **Server Component** (no `onLoad`/`onReady` handlers ⇒ no `"use client"` needed, per `scripts.md` L270). |
| Event API           | `sendGAEvent` → `dataLayer`.                                                                                                                                                              | `window.gtag(...)` directly — and US00144's listener is our own client component either way, so this buys nothing.                       |
| Total code replaced | ~25 lines                                                                                                                                                                                 | —                                                                                                                                        |

Adding an experimental dependency to save ~25 lines, on the one component that must not break the launch build, is the wrong trade. **Recorded as decision D1.**

### D2 — The env var cannot be read from `lib/env.ts` on the client

`environment-variables.md` L186–195 states verbatim that dynamic lookups are **not** inlined:

```js
// This will NOT be inlined, because it uses a variable
const varName = "NEXT_PUBLIC_ANALYTICS_ID";
setupAnalyticsService(process.env[varName]);
```

`lib/env.ts`'s `optionalEnvVar(name)` is exactly `process.env[name]` — a dynamic lookup. So `env.NEXT_PUBLIC_GA_MEASUREMENT_ID` is **server-only in practice**, despite the `NEXT_PUBLIC_` prefix.

This is not a defect to fix — it is the design constraint that shapes the story:

> **The gate is evaluated in a Server Component (the root layout / a server helper) and the resolved ID is passed down as a prop. No client component ever reads `process.env` for the measurement ID.**

That satisfies spec §6 (_"US00143 consumes the existing plumbing rather than adding its own `process.env` read"_) without a `lib/env.ts` change, and it is also strictly better for Scenario 2: with no ID, the client bundle contains no analytics code at all rather than dead-but-shipped code.

`NODE_ENV` is the one exception — `process.env.NODE_ENV` is a literal static reference and Next inlines it normally. It is nonetheless also evaluated server-side here, for the same reason.

## 3. Design

### 3.1 `lib/analytics.ts` (new)

```ts
import { env } from "@/lib/env";

/** GA4 measurement IDs are `G-` followed by an alphanumeric property token. */
const GA_MEASUREMENT_ID_PATTERN = /^G-[A-Z0-9]{4,}$/;

/**
 * The one place that decides whether GA4 is active.
 *
 * SERVER-ONLY. `lib/env.ts` reads `process.env[name]` with a dynamic key, which
 * Next.js does NOT inline into the client bundle (see the env-var guide,
 * "dynamic lookups will not be inlined"). Call this from a Server Component and
 * pass the result down as a prop — never import it into a "use client" module.
 *
 * Returns undefined when analytics must not load: no ID configured, or any
 * non-production NODE_ENV (US00143 Scenario 3 — local browsing must never
 * pollute production data).
 *
 * Throws when an ID is set but malformed: that is a deployment misconfiguration
 * worth failing the build over, and it also closes the injection vector for the
 * value interpolated into the inline <Script> below.
 */
export function resolveGaMeasurementId(): string | undefined {
  const id = env.NEXT_PUBLIC_GA_MEASUREMENT_ID;
  if (!id) return undefined;
  if (!GA_MEASUREMENT_ID_PATTERN.test(id)) {
    throw new Error(
      `NEXT_PUBLIC_GA_MEASUREMENT_ID must look like "G-XXXXXXXXXX". Received: "${id}"`,
    );
  }
  if (process.env.NODE_ENV !== "production") return undefined;
  return id;
}
```

Order matters: validate **before** the `NODE_ENV` bail-out, so a typo'd ID in `.env.local` surfaces in dev instead of hiding until production.

The GA4 event name and payload keys for US00144 will be added to this same file — flagged here so the successor story extends rather than creates a parallel module.

### 3.2 `components/GoogleAnalytics.tsx` (new, Server Component)

```tsx
import Script from "next/script";

export function GoogleAnalytics({ measurementId }: { measurementId: string }) {
  return (
    <>
      <Script
        src={`https://www.googletagmanager.com/gtag/js?id=${measurementId}`}
        strategy="afterInteractive"
      />
      <Script id="ga4-init" strategy="afterInteractive">
        {`window.dataLayer = window.dataLayer || [];
function gtag(){dataLayer.push(arguments);}
gtag('js', new Date());
gtag('config', '${measurementId}');`}
      </Script>
    </>
  );
}
```

- **No `"use client"`.** `scripts.md` L270 restricts only `onLoad`/`onReady`/`onError` to Client Components; we use none.
- **`strategy="afterInteractive"`** — the documented default and the correct one for an analytics tag: loaded early, but never blocking hydration. Not `beforeInteractive` (would delay first paint for a tracker); not `lazyOnload` (would lose short-session page views).
- **`id="ga4-init"` is mandatory** on the inline script — `script.md` L258: _"An `id` property must be assigned for inline scripts in order for Next.js to track and optimize the script."_
- The `${measurementId}` interpolation is safe because §3.1 has already constrained it to `/^G-[A-Z0-9]{4,}$/`.
- No co-located `.module.css` — this component renders no markup.

### 3.3 `app/layout.tsx` (modify)

```tsx
import { resolveGaMeasurementId } from "@/lib/analytics";
import { GoogleAnalytics } from "@/components/GoogleAnalytics";

export default function RootLayout({ children }: { children: React.ReactNode }) {
  const gaMeasurementId = resolveGaMeasurementId();
  return (
    <html lang="vi">
      <body>
        {/* … existing SkipLink / Header / main / Footer / SpeedInsights … */}
        {gaMeasurementId && <GoogleAnalytics measurementId={gaMeasurementId} />}
      </body>
    </html>
  );
}
```

Placed last in `<body>`, next to the existing `<SpeedInsights />` — same category of thing, same position, and `afterInteractive` makes DOM position irrelevant to load order anyway.

The layout stays a Server Component with no request-time API (`cookies()`, `headers()`, `searchParams`), so **nothing here can flip a route to `ƒ`** — that is Scenario 4, and §4 step 5 verifies it rather than assuming it.

- `app/layout.tsx` entry — append the conditional `<GoogleAnalytics />` mount.

New **module convention** to record under "Module conventions":

> **Analytics gating lives in one place: `lib/analytics.ts`.** No file outside it may read `NEXT_PUBLIC_GA_MEASUREMENT_ID` or decide whether analytics is enabled. It is **server-only** by construction — `lib/env.ts` reads `process.env[name]` dynamically, which Next.js does not inline into client bundles, so the measurement ID must be resolved in a Server Component and passed down as a prop. A `"use client"` module must never import it.

## 6. Risks & edge cases

- **R1 — Invalid measurement ID.** Spec §5 notes GA silently drops data for a wrong-but-well-formed ID; the shape guard (§3.1) only catches gross malformation. This is exactly why Scenario 1 is verified against **GA4 Realtime**, not against a script tag (§4 step 9.4).
- **R2 — `page_view` on client-side navigation.** App Router `<Link>` navigations do not reload the document, so the single `gtag('config')` call fires one `page_view`. GA4's **Enhanced measurement → "Page changes based on browser history events"** is on by default and covers this. Confirm it is enabled in the data stream at step 9.1; if it is not sufficient in Realtime testing, the follow-up is a small `usePathname()` effect inside a client child of `<GoogleAnalytics>` — **not** part of this story.
- **R3 — Ad blockers.** Expected in the VN market; spec §5 accepts it. Realtime verification must be done in a browser with blocking disabled or the analytics domains allow-listed, otherwise step 9.4 fails for the wrong reason.
- **R4 — Vercel Preview deployments run `NODE_ENV=production`.** The `NODE_ENV` gate alone will not keep Preview traffic out of the production property. Mitigated by scoping the env var to the Production environment only (§4 step 9.2).
- **R5 — Frozen at build time.** `NEXT_PUBLIC_*` values are baked into the bundle by `next build`; setting the var without redeploying does nothing. Called out at step 9.3 because it is the most common way this appears "broken".
- **R6 — CSP.** The repo ships no Content-Security-Policy header today, so the inline `ga4-init` script needs no nonce. If a CSP is ever added, this script is the first thing it will break.
