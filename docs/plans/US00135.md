## 1. Scope

Strictly:

1. Make the placeholder in `.env.example` / `.env.local` / `.github/workflows/ci.yml` unambiguous — a reader must not mistake `https://example.com` for a real configured value.
2. Add a **verification script**, `scripts/verify-canonical.ts` (`npm run verify:canonical`), that fetches a deployed site and asserts no `example.com` (or any non-target host) survives in `/sitemap.xml`, `/robots.txt`, and the canonical / `og:url` / JSON-LD `url` of one product, one post and one category page.
3. Add a **swap-day checklist** to `docs/plans/US00135.md` (this file) + a short operator section in `README.md`.
4. Leave `lib/env.ts`, `lib/seo.ts` and every metadata call site **untouched** — the plumbing is already correct (US00091/US00092); only the value is wrong.
5. **(Added 2026-09-02, Scenario 4)** Rename site branding to match the registered domain: `lib/site.ts`'s `SITE_NAME` constant `"aff-store"` → `"MuaGear"`, and `package.json`'s `"name"` field `"aff-store"` → `"muagear"`. `SITE_NAME` is already the single chokepoint consumed by Header, Footer, `buildRootMetadata()`'s title template, and every `Organization`/publisher JSON-LD reference — no call site needs touching beyond the constant itself.

**Explicitly out of scope:**

- Buying/pointing the domain, Vercel dashboard configuration (operator actions) — the domain purchase itself is done; DNS/Vercel wiring is Half B.
- Google Search Console verification + sitemap submission — **F0014/US00144**.
- Any change to how canonical URLs are composed. `lib/seo.ts` is the single chokepoint and stays as-is.
- Adding a build-time "reject example.com" guard in `lib/env.ts` — see **D4**; it would break CI and local dev, which legitimately use the placeholder.
- Any visual/logo/favicon redesign — `SITE_NAME` is a text string; a visual rebrand is a separate, undecided piece of work.
- Repository/GitHub remote rename (`aff-store` repo name itself) — not requested; only in-app branding and the npm package identifier.

## 3. Approved Decisions

| # | Decision | Choice | Rationale |
| --- | --- | --- | --- |
| D1 | Placeholder wording | Change `.env.example` to `NEXT_PUBLIC_SITE_URL=https://example.com` **plus** an explicit `# PLACEHOLDER — replace with the real production domain. Production must never ship this value.` comment | Scenario 3: a contributor must see at a glance that it is a placeholder, not a configured value. |
| D2 | CI value | Keep `https://example.com` in the `build` job, add a comment: `# Build smoke test only — canonical URLs are not asserted here. Real value lives in Vercel Production env.` | Scenario 3 explicitly says CI must still build without a real domain. |
| D3 | Verification mechanism | A committed script `scripts/verify-canonical.ts` run against a deployed URL (`npm run verify:canonical -- --base=https://<domain>`), not a manual click-through | Scenario 2 lists six concrete artefacts to check; a script makes the check repeatable and re-runnable after every future domain change. Manual checking is how the 1×1 covers shipped. |
| D4 | No build-time `example.com` rejection | Do **not** add a guard in `lib/env.ts` that throws on `example.com` | It would break the CI `build` job (D2) and every local `next build`. The real gate is the deployed-output check (D3), which runs where the value actually matters. |
| D5 | Which pages the script samples | One product, one post, one category — chosen **dynamically** from the fetched `sitemap.xml` rather than hardcoded slugs | US00131 renames product slugs; hardcoded sample URLs would rot within the same feature. |
| D6 | Failure mode | Exit non-zero, printing every offending URL + the artefact it was found in | Same fail-loudly-and-name-it style as `assertAffiliateUrl` / `assertCategoryRegistered`. |
| D7 | Trailing slash | Assert `NEXT_PUBLIC_SITE_URL` has scheme + host and **no** trailing slash; the script normalizes `--base` the same way | Spec Scenario 1 wording; `absoluteUrl()` composes `${base}${path}` so a trailing slash yields `//`. |
| D8 | Story completion | Half A ships as a PR; the story stays **In Progress** until Half B's script run is green against the live domain and pasted into the PR/issue | Prevents "verified" being claimed against a domain that does not exist. |
| D9 | Branding rename scope | Rename only the text constant (`SITE_NAME`) and the npm package identifier; no logo/favicon/visual redesign, no GitHub repo rename | 2026-09-02 decision: bundle branding into US00135 since it's the same "things tied to the domain" bucket, but keep the change mechanical (one constant + one field) rather than opening a design workstream inside a verification-shaped story. |

## 10. Risks / open items

- **R1 — Story cannot close until the domain exists.** Mitigated by D8: Half A ships value now (an executable checklist beats a wiki page), Half B is a 6-step run. Track the open half in `docs/BACKLOG.md` so it does not get lost behind a merged PR.
- **R2 — Redeploy forgotten.** `NEXT_PUBLIC_*` values are inlined at build; changing the Vercel env var without redeploying leaves `example.com` live. §6 step 3 calls this out explicitly and step 4 catches it.
- **R3 — Script brittleness against HTML.** Regex extraction of `<link rel="canonical">` / `og:url` could miss an attribute-order variant. Mitigated by also doing the blunt whole-body `example.com` substring check (D3), which cannot be evaded by markup shape.
- **R4 — Preview deployments.** Vercel Preview envs will keep whatever value is set for Preview; canonicals on preview URLs pointing at production is standard and *desirable* (avoids duplicate indexing). Do not "fix" this.
- **R5 — Slug-change window (spec §6).** Once Half B lands and crawling starts, any further URL change needs redirects the SSG-only site has no mechanism for. **US00131 (product slugs) and US00132 (removed category URLs) must both be merged before Half B runs** — this is precisely why the domain story sits last in the dependency order rather than first. (Both are already merged as of 2026-09-02, per `docs/BACKLOG.md` — Half B is unblocked.)
- **R6 — Partial `SITE_NAME` rename.** A missed reference would leave "aff-store" visible somewhere in production (Header, `<title>`, or a JSON-LD field) while the domain reads `muagear.com` — a worse inconsistency than not renaming at all. Mitigated by the grep-for-leftover-string step (§5 step 3) before the PR, since `SITE_NAME` is already the sole chokepoint (no call site to individually check).
