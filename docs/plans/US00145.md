## 0. What kind of story this is

Mostly **not code.** Three of four scenarios are console operations. The repository contribution is:

- a **conditional** code path (only if DNS verification is unavailable — §3),
- a written, repeatable operator checklist (§4) that lives in `README.md` next to the existing "Setting the production domain" section,
- the recorded evidence that the checklist was run.

Spec §6 is explicit: *"US00145 is entirely a console operation… these stories are not 'done' at merge — they are done when the sitemap report is observed."*

## 2. D1 — Property type and verification method

Two decisions, taken together because they interact.

**Property type: create a `muagear.com` *Domain* property.**

The site is served on `www.muagear.com` while the apex 308-redirects to it. A **URL-prefix** property is per-scheme-and-host: `https://www.muagear.com/` and `https://muagear.com/` would be *two separate properties*, and picking the wrong one yields an empty-looking report. A **Domain property** covers every subdomain and both schemes in one, which exactly matches this setup. It is also the only property type that *requires* DNS verification — which is the method spec Scenario 1 already prefers.

**Verification method: DNS TXT.** Spec Scenario 1: *"via DNS TXT record (preferred: no code change, survives any hosting change)"*, and spec §5: *"DNS TXT verification survives a Vercel project change; a meta tag does not survive an env var being cleared."* Since the domain was registered for this project, DNS access exists.

> **If and only if DNS TXT proves unavailable**, fall back to the URL-prefix property `https://www.muagear.com/` with meta-tag verification — and then §3 applies. Decide this at step 4.1 before writing any code.

## 3. Conditional code path (meta-tag fallback only)

Do **not** write this unless D1's fallback is taken. If it is, Scenario 2 forbids hand-writing the tag; it must flow through the existing chokepoints.

**3.1 `lib/env.ts`** — one new optional entry:

```ts
export const env = {
  NEXT_PUBLIC_SITE_URL: requireUrl("NEXT_PUBLIC_SITE_URL"),
  NEXT_PUBLIC_GA_MEASUREMENT_ID: optionalEnvVar("NEXT_PUBLIC_GA_MEASUREMENT_ID"),
  GOOGLE_SITE_VERIFICATION: optionalEnvVar("GOOGLE_SITE_VERIFICATION"),
} as const;
```

**Deliberately no `NEXT_PUBLIC_` prefix.** The value is consumed only by `buildRootMetadata()`, which runs in a Server Component at build time; it never needs to reach the browser bundle. (The token is public in the served HTML either way — this is about not shipping it into client JS, and about not implying client access.) Note this differs from `NEXT_PUBLIC_GA_MEASUREMENT_ID`, which is also only read server-side today — that one keeps its historical prefix.

**3.2 `lib/seo.ts` → `buildRootMetadata()`** — add one field to the returned `Metadata`:

```ts
import { env } from "@/lib/env";
// …
    ...(env.GOOGLE_SITE_VERIFICATION
      ? { verification: { google: env.GOOGLE_SITE_VERIFICATION } }
      : {}),
```

Next.js `Metadata` has a first-class `verification.google` field that renders `<meta name="google-site-verification" content="…" />` (confirmed in `node_modules/next/dist/docs/01-app/03-api-reference/04-functions/generate-metadata.md` §`verification`, L756–775). Spread conditionally so an unset var emits **nothing** rather than an empty-content tag.

**3.3 `.env.example`** — document it:

```
# Optional — Google Search Console meta-tag verification token.
# Only needed if DNS TXT verification is unavailable (US00145). Leave empty otherwise.
GOOGLE_SITE_VERIFICATION=
```

**3.4 `lib/seo.test.ts`** — one test each: unset ⇒ no `verification` key in the returned metadata; set ⇒ `verification.google` equals the value.

**3.5 Structure-doc** — extend the `lib/env.ts` and `lib/seo.ts` entries in `CLAUDE.md` + `README.md`, and add to the "Page metadata is built in one place" bullet:

> The Search Console verification token, when meta-tag verification is used, is `GOOGLE_SITE_VERIFICATION` in `lib/env.ts`, emitted via `buildRootMetadata()`'s `verification.google`. No route or component may hand-write a `<meta name="google-site-verification">` tag.

## 4. Operator checklist (the story proper)

Run against **production**, in order. Record each result.

1. **Choose the path.** Confirm DNS record access for `muagear.com` at the registrar. Yes ⇒ Domain property + DNS TXT (steps 2–3). No ⇒ §3 code path, merge and redeploy first, then URL-prefix property + meta tag.
2. **Create the property.** Search Console → Add property → **Domain** → `muagear.com`.
3. **Verify ownership.** Copy the `google-site-verification=…` TXT record into the registrar's DNS for the apex; wait for propagation (`dig TXT muagear.com +short` shows it); click Verify. *(Fallback path: paste the token into Vercel Production as `GOOGLE_SITE_VERIFICATION`, **redeploy** — the value is baked at build time — confirm the meta tag with `curl -s https://www.muagear.com/ | grep google-site-verification`, then click Verify.)*
4. **Submit the sitemap.** Sitemaps → enter `sitemap.xml` → Submit. Confirm status **Success**, "Sitemap could not be read" absent.
5. **Reconcile the count (Scenario 3).** `curl -s https://www.muagear.com/sitemap.xml | grep -c "<loc>"` must equal Search Console's "Discovered URLs". Expect **28** today; if they differ, the discrepancy — not the spec's 29 — is the finding.
6. **Crawlability spot-check (Scenario 4).** URL Inspection on **one of each**:
   - product — e.g. `https://www.muagear.com/san-pham/logitech-g305-lightspeed-wireless/`
   - post — e.g. `https://www.muagear.com/bai-viet/top-5-chuot-gaming-gia-re/`
   - category — e.g. `https://www.muagear.com/danh-muc/chuot-gaming/`

   Each must report **"URL is available to Google"** / crawl allowed. Pull the live slugs from the sitemap rather than trusting the examples above.
7. **robots.txt (Scenario 4).** `curl -s https://www.muagear.com/robots.txt` — `Allow: /`, and `Sitemap: https://www.muagear.com/sitemap.xml` on the production host. Also check Search Console → Settings → robots.txt for a "Fetched" status.
8. **Request indexing** for the homepage and one post to prime the crawler. Not an acceptance criterion; free and useful on launch day.
9. **Record the evidence.** Screenshots (verification success, sitemap Success + discovered count, three URL-inspection results) attached to the PR or appended to this plan as a §6 log, mirroring how `docs/plans/US00135.md` §6 logged its swap-day run. **The story is Done only after step 5 and step 6 both pass.**

Add steps 1–8, condensed, as a **"Search Console"** subsection in `README.md` immediately after "Setting the production domain" — the two are the same swap-day ritual and belong together.

## 6. Risks

- **R1 — Wrong property type.** With the apex redirecting to `www`, a URL-prefix property on the apex would look permanently empty. D1's Domain property is the mitigation; if the fallback forces URL-prefix, it **must** be `https://www.muagear.com/` (the host that actually serves), not the apex.
- **R2 — DNS propagation lag.** Verification can fail for up to ~24h purely on propagation. Verify with `dig` before clicking Verify; a failed click is retryable, not fatal.
- **R3 — Meta tag lost to a cleared env var (fallback only).** Spec §5's exact warning. If the fallback is used, note in `README.md` that clearing `GOOGLE_SITE_VERIFICATION` un-verifies the property, and revisit DNS verification when access becomes available.
- **R4 — Sitemap count drift.** Every new product/post changes the number. Scenario 3 is a point-in-time reconciliation, not a standing invariant — do not encode 28 anywhere in code or tests.
- **R5 — Search Console lag.** Coverage and query data take days. Scenarios 3 and 4 are checkable immediately; index coverage is not, and waiting for it is not part of this story's definition of done.
- **R6 — Ordering vs US00143/US00144.** Independent. This story can run before or after the analytics stories; it only needs a live, correctly-domained deploy.
