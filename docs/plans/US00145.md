## 1. Risk assessment done at planning time

The only genuinely risky slice is `content/` — those files feed build-time guards. Dry-run on the largest post:

```
$ cp content/posts/top-5-chuot-gaming-gia-re.mdx /tmp/t.mdx && npx prettier --write /tmp/t.mdx
$ diff content/posts/top-5-chuot-gaming-gia-re.mdx /tmp/t.mdx   # 16 lines
```

The **entire** diff is GFM table-cell padding (`| Sản phẩm |` → `| Sản phẩm                   |`). Semantically identical markdown, no prose rewrapping (`proseWrap: "preserve"` holds), no change to `<ProductCard slug>` embeds or frontmatter. Padding adds only whitespace, so `countWords()` (`lib/format.ts`) — and therefore `MIN_POST_WORDS` in `lib/posts.test.ts` (US00134) — is unaffected.

`content/products/*.json` reformatting is key-order-preserving whitespace only; `lib/products.ts` parses with `JSON.parse`, so it cannot be affected.

**Conclusion: no `.prettierignore` addition is needed.** Formatting `content/` is safe and is verified empirically in §3 step 4, not assumed.

## 2. Scope

1. One repository-wide `prettier --write .` applied as an **isolated commit** containing nothing else.
2. A `.git-blame-ignore-revs` file recording that commit's SHA.
3. A `format` job in `.github/workflows/ci.yml`.
4. A short README note so `git blame` users know to configure `blame.ignoreRevsFile`.

**Out of scope:** adding a Prettier plugin, changing any `.prettierrc` option, changing `.prettierignore` (unless §3 step 4 surfaces an actual breakage), adding a pre-commit hook / husky / lint-staged, formatting `package-lock.json`.

## 3. Step-by-step execution order

Branch `feat/US00145-format-baseline` off `main` **after US00143 is merged**.

**PR 1 / commit 1 — the baseline (formatting only).**

1. Confirm a clean tree and a green starting point, and **capture the pre-change build route table** for the Scenario-4 comparison:
   ```
   git status --porcelain          # must be empty
   npm run typecheck && npm run lint && npm test
   npm run build 2>&1 | tee /tmp/build-before.txt
   ```
2. `npm run format:fix`
3. `git diff --stat` — sanity-check the file count lands near 166 and that **no** file outside the §0 table appears.
4. **Content-safety check** (the one step that must not be skipped):
   ```
   git diff --stat content/
   git diff content/posts/     # eyeball: whitespace/table padding only
   npm test                    # US00133 cover guard + US00134 depth guard + all others
   ```
   Any semantic change to an `.mdx` body — a reflowed paragraph, a mangled `<ProductCard …/>`, a touched frontmatter value — stops this story and is resolved by adding a targeted `.prettierignore` entry, not by hand-editing the formatted output.
5. Commit **only** formatting:
   ```
   git commit -am "style: apply repository-wide Prettier baseline (US00145)

   Formatting only — no behavioral change. Recorded in .git-blame-ignore-revs.

   Co-Authored-By: Claude Opus 5 <noreply@anthropic.com>"
   ```
6. Push, open **PR 1** (`feat/US00145-format-baseline`), let CI go green, merge it.
   Then capture the SHA **as it landed on `main`** — not the branch-local one:
   ```
   git checkout main && git pull
   git log -1 --format=%H            # ← this is the SHA that goes in .git-blame-ignore-revs
   ```
   Cut `feat/US00145-format-gate` from this updated `main` for PR 2.

**PR 2 / commit 2 — the gate and the blame-ignore file.** Opened only after PR 1 is merged, off a branch cut from the updated `main`.

7. Create `.git-blame-ignore-revs`:
   ```
   # Revisions to ignore in `git blame` — formatting-only, no behavioral change.
   # Enable locally with:
   #   git config blame.ignoreRevsFile .git-blame-ignore-revs
   #
   # US00145 (F0014) — repository-wide Prettier baseline, 2026-09-03 (166 files).
   <sha-from-step-6>
   ```
   The file must contain **full 40-char SHAs**; `git blame` rejects abbreviated ones.
8. Add the `format` job to `.github/workflows/ci.yml`, matching the existing job shape exactly (same rationale as US00143 §3):
   ```yaml
     format:
       name: format
       runs-on: ubuntu-latest
       steps:
         - uses: actions/checkout@v4
         - uses: actions/setup-node@v4
           with:
             node-version-file: ".nvmrc"
             cache: "npm"
         - run: npm ci
         - run: npm run format
   ```
   `prettier --check` already exits non-zero listing each offending path by name, so Scenario 2's "fails naming the offending file" needs no extra flag.
9. Add a short **Formatting** subsection to `README.md` (near the existing contributor/workflow notes) documenting `npm run format` / `npm run format:fix` and the one-time
   `git config blame.ignoreRevsFile .git-blame-ignore-revs`.
10. Commit, push, open **PR 2**.

**Verification (Scenario 4).**

11. On the branch tip: `npm run typecheck && npm run lint && npm test && npm run build`.
12. `diff <(grep -E '^[│├└]|Route|○|●|ƒ' /tmp/build-before.txt) <(...after...)` — or simply diff the two route tables by eye. **Every route must still be `○`/`●`; zero `ƒ`.** Paste both tables into the PR description.
13. Scenario 2 evidence: on a scratch branch off this one, introduce a deliberately unformatted file (e.g. `lib/format.ts` with a double blank line and 4-space indent), push, confirm the `format` check goes red naming that file, then delete the scratch branch and its draft PR. Do not merge it.

## 6. Risks

- **Merge conflicts with any open branch.** A 166-file reformat conflicts with everything. Confirm `git branch -r` shows no in-flight feature branch before starting; if one exists, land or close it first. This is spec §5's explicit warning.
- **Squash-merge invalidates the recorded SHA — and this repo squash-merges today (confirmed).** `git log -5 --pretty="%h %p"` on `main` shows every recent PR (#68, #70–#73) landed as a **single-parent commit with a `(#NN)` suffix**, i.e. squash merges; the last true merge commits are from PR #15. So the SHA written in step 7 is a branch-local commit that will **never appear on `main`**, and `.git-blame-ignore-revs` would point at nothing — Scenario 3 would ship silently broken.

  **Resolved 2026-09-03: option (A).**

  - **(A) ✅ CHOSEN — two PRs.** PR 1 = the reformat only. Merge it, then `git log -1 --format=%H origin/main` gives the real `main` SHA. PR 2 = `.git-blame-ignore-revs` (with that SHA) + the `format` CI job + the README note + the structure-doc updates. Works under squash-merge with no policy change, and keeps the baseline commit genuinely isolated on `main` — which is what Scenario 3 actually asks for.
  - **(B) rejected — one PR merged with a merge commit or rebase** instead of squash. Would preserve both SHAs but requires deviating from the repo's merge habit for this one PR.

  §3 is written accordingly: the same steps, split at the PR 1 / PR 2 boundary.
- **CI job count 4 → 5.** Accepted by spec §5.
- **`docs/` is 71 of the 166 files.** Reformatting markdown specs and plans is noisy but harmless; it is also why the isolated-commit requirement exists.
