# Implementation Plan — US00153: Supersede the previous week's post on a new run

**Status:** Approved
**Feature:** F0015 — Weekly Deal Roundup Content
**Spec ref:** `docs/specs/F0015.md` § US00153
**Predecessors:** **US00152 (hard)** — builds on `lib/deals.ts` and on the `{/* roundup-lead:… */}` markers the generator emits.
**Successors:** US00154 (sequences this after generation).

---

## 0. The state machine spec §6 forbids, and how to avoid needing one

Spec §6: _"Supersession is a content rewrite, not a new mechanism … no new 'post status' field, no CMS-like state machine. This keeps the feature consistent with the project's file-is-the-database model."_

But Scenario 3 requires every "latest/related" surface to distinguish the _current_ roundup from _archived_ ones. Something has to know the difference. **D6 — derive it; never store it.** Two facts already on disk are enough:

1. A post **is a roundup** iff `content/deals/<slug>.json` exists — i.e. `postHasDeals(slug)` from `lib/deals.ts` (US00152). No naming convention is trusted, no frontmatter flag is added.
2. Among a category's roundups, the **current** one is simply the newest `publishedAt`. Every other one is archived.

Both are pure functions of existing artefacts. No field, no status, nothing to keep in sync — and a hand-deleted sidecar demotes its post automatically rather than leaving a lying flag behind.

**D7 — Archived roundups are demoted from the homepage strip and related-posts only.** Approved 2026-09-07. They stay in `/bai-viet/` and in `sitemap.xml`. Scenario 3 names the blog listing too, but filtering them there as well would leave an archived post with **no internal link path at all** — self-defeating for pages the same scenario insists must remain _"reachable (not deleted, not `noindex`)"_. The blog listing is the archive; the homepage and related-posts are the promotion surfaces, and those are what cannibalize.

## 1. Scope

1. `lib/roundups.ts` — the one place that decides roundup / current / archived.
2. `lib/roundups.test.ts`.
3. Two call sites: `app/page.tsx` (homepage `<LatestPosts>`) and `app/bai-viet/[slug]/page.tsx` (`getRelatedPosts` pool).
4. `scripts/deal-roundup/supersede.ts` — the in-place rewriter.
5. `scripts/deal-roundup/supersede.test.ts`.
6. Wiring the rewriter into `scripts/generate-deal-post.ts`, **after** a successful write.

**Out of scope:** `noindex` / deindexing archived posts (spec §2, explicitly deferred); removing archived posts from `sitemap.xml`, `/bai-viet/`, or `getAllPosts()`; any diffing of week-over-week deal movement (spec §5: _"no diffing/callout required in v1"_); the slash command (US00154).

## 3. Design

### 3.1 `lib/roundups.ts`

```ts
/** A post is a roundup iff it has a deal sidecar — derived, never stored (D6). */
export function isRoundupPost(post: Post): boolean {
  return postHasDeals(post.slug);
}

/**
 * The current (non-archived) roundup slug per category: the newest publishedAt
 * among that category's roundups. Ties break on slug descending, which cannot
 * occur in practice — a roundup slug carries its date and same-day re-runs
 * overwrite in place (US00152 D6) — but keeps the result deterministic for SSG.
 */
export function currentRoundupSlugs(posts: Post[]): Set<string>;

/**
 * Drop archived roundups from a promotion surface. Non-roundup posts and the
 * current roundup per category always pass through, order preserved.
 *
 * Applied at the CALL SITE of each promotion surface — the homepage strip and
 * the related-posts pool — never inside getAllPosts(). /bai-viet/ and
 * sitemap.xml must keep listing archived roundups (D7).
 */
export function demoteArchivedRoundups(posts: Post[]): Post[];
```

`lib/roundups.ts` imports `lib/deals.ts` and the `Post` type only — it never imports `lib/posts.ts`, so there is no import cycle (`lib/posts.ts` stays unaware of F0015 entirely).

### 3.2 Call sites — two lines, both explicit

`app/page.tsx`:

```tsx
<LatestPosts posts={demoteArchivedRoundups(posts)} />
```

`app/bai-viet/[slug]/page.tsx`:

```tsx
const related = getRelatedPosts(post, demoteArchivedRoundups(all));
```

**Why the call site and not inside `getRelatedPosts`.** `lib/posts.ts` is the loader every surface depends on; teaching it about deal roundups would mean `/bai-viet/`, the sitemap and `generateStaticParams` all inherit a filter they must _not_ have. Filtering the _pool passed in_ keeps the blast radius to exactly the two promotion surfaces Scenario 3 names, and makes the demotion visible in the page code rather than hidden in a shared loader. `<LatestPosts>` and `<RelatedPosts>` themselves are unchanged — they render whatever list they are handed.

An archived roundup's **own** page still renders `<RelatedPosts>` normally; the _current_ roundup for its category legitimately appears there, which is a link from archive → current. That is the correct direction and needs no special-casing.

### 3.3 `scripts/deal-roundup/supersede.ts`

```ts
export interface SupersedeResult {
  /** null when the category had no prior roundup — a first run (Scenario 1). */
  supersededSlug: string | null;
  /** true when the prior post was already in archived framing (same-day re-run). */
  alreadyArchived: boolean;
}

export function supersedePriorRoundup(
  category: string,
  currentPostSlug: string,
  opts?: { postsDir?: string },
): SupersedeResult;
```

Steps:

1. Load posts; keep roundups in `category` whose slug ≠ `currentPostSlug`; take the newest `publishedAt`. None ⇒ `{ supersededSlug: null }` — **Scenario 1**: a first run creates the evergreen post and rewrites nothing.
2. Read the file with `gray-matter`. Compute the archive date string via **`formatArchiveDate(post.publishedAt)`**, a new export in `lib/format.ts` producing `31/08/2026`.
   `CLAUDE.md`: _"No file outside `lib/format.ts` may call `toLocaleDateString`, `Intl.DateTimeFormat`, or hand-roll a … string on a post date."_ `dd/mm/yyyy` is a different format from `formatPostDate`'s `"31 tháng 8, 2026"`, so it is a **new function in the existing chokepoint**, not a second date formatter elsewhere. Same regex-split, no `Intl`, deterministic across build pools.
3. **Rewrite three things** (Scenario 2 is explicit that metadata alone is not enough):
   - `title` (which _is_ the H1 — see D7 below): `"… trên Shopee tuần này"` → `"… trên Shopee (31/08/2026)"`.
   - `summary` (the meta description): same substitution, then assert the result is still 50–160 chars so `lib/posts.test.ts` cannot be broken by the rewrite.
   - The **lead paragraph**, replacing everything between `{/* roundup-lead:start */}` and `{/* roundup-lead:end */}` with archived-framing copy naming the date: _"Bài viết này tổng hợp các deal … ghi nhận ngày 31/08/2026. Xem bản mới nhất tại …"_ — plus a Markdown link to the current roundup, which is the internal link that keeps the archived page connected (D7).
4. Write the file back. Everything else — body prose, deal cards, sidecar, `publishedAt`, `coverImage`, `tags` — is untouched. The sidecar is **never** rewritten: the archived post keeps rendering the deals it was published with, which is what the price disclaimer already covers.

**D7 — the "H1" is frontmatter `title`.** `app/bai-viet/[slug]/page.tsx:76` renders `<h1>{post.title}</h1>`; MDX bodies contain no `h1` (and `lib/posts.test.ts` requires `h2` sections, not an `h1`). So Scenario 2's "H1 and lead paragraph, not only its `<title>`/meta description" is: **frontmatter `title` + frontmatter `summary` + the lead paragraph** — and because `title`/`summary` flow through `buildPageMetadata`, `buildArticleSchema` and `buildPostBreadcrumbs`, the visible H1, the `<title>`, `og:title`, the Article JSON-LD `headline` and the breadcrumb label all change from one edit, through the existing chokepoints. No new SEO code path, exactly as spec §6 requires.

**Idempotency.** Re-running (spec §5's same-day re-run) must not double-append. Before rewriting, if `title` already matches `/\(\d{2}\/\d{2}\/\d{4}\)$/`, return `{ alreadyArchived: true }` and touch nothing.

**Missing markers are fatal, not silent.** If the lead markers are absent — a human deleted them while writing prose — `supersedePriorRoundup` throws, naming the file and the marker text. Silently rewriting only the frontmatter would leave the archived page's _on-page content_ still targeting "tuần này", which is precisely the failure Scenario 2 was written to prevent. The failure surfaces before any commit, and both files are left visible in the working tree (US00154 Scenario 2). `/deal-roundup`'s rules will state that the markers must survive prose writing.

### 3.4 Ordering inside `generate-deal-post.ts`

```
load deals → 0 usable? report + exit 0, NO supersede   (spec §5, first bullet)
           → stage images (all-or-nothing, D5b)
           → write sidecar + MDX
           → supersedePriorRoundup(...)                 ← only now
```

Supersession is the **last** write and runs only after the current post exists on disk. This is what makes _"never left with the prior post silently relabeled while no current post exists"_ (US00154 Scenario 2) structurally true rather than a matter of care.

### 3.5 `countWords` note

The `{/* … */}` strip in `lib/format.ts`'s `countWords()` was moved into **US00152** (where the markers are first emitted) rather than here, so the lead markers never inflate a word count against the depth floor. Nothing further is needed in this story.

## 7. Risks & edge cases

- **R1 — A human deletes the lead markers while writing prose.** The single most likely way this story silently fails. Made loud in §3.3 (throw, naming the file), and stated as a rule in `/deal-roundup`. Considered and rejected: falling back to "rewrite the first paragraph" — it would quietly rewrite the wrong text once someone reorders the body.
- **R2 — The two-post-per-category window.** Between generation and supersession there is a moment when two "tuần này" posts exist on disk. It never reaches production: both are uncommitted, and §3.4's ordering plus US00154's build-then-push means a failed run is discarded before push, not deployed.
- **R3 — Archived posts still competing in Search Console.** Spec §2 explicitly defers `noindex` to a follow-up. This story's rewrite plus the demotion is v1; if Search Console still shows two URLs for one query in a few weeks, that follow-up is the fix — not a quiet expansion here.
- **R4 — Demotion applied too broadly.** Filtering inside `getAllPosts()` would silently strip archived roundups from `sitemap.xml` and `generateStaticParams`, deindexing them by accident — the exact opposite of spec §2. The call-site design (§3.2) plus the "no roundups at all ⇒ list unchanged" test are the guards.
- **R5 — A category's roundup cadence lapses.** If a category is skipped for a month, its most recent roundup stays "tuần này"-framed and promoted while being a month old. Correct per spec §5 (_"the site never goes a week showing a stale-dated post as current when nothing new was found"_), but worth an operator note in `scripts/README.md`: a lapsed category should be re-run or its roundup manually archived.
- **R6 — Summary length after rewrite.** Substituting `"tuần này"` → `"(31/08/2026)"` lengthens the string by 4 characters; a summary already near 160 could overflow the `lib/posts.test.ts` bound. Asserted in §3.3 step 3 and covered by a test, and the generator's template leaves headroom.
