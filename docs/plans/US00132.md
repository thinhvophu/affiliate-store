# Implementation Plan — US00132: Resolve zero-product categories

**Status:** Approved
**Feature:** F0013 — Launch Content Remediation
**Spec ref:** `docs/specs/F0013.md` § US00132
**Predecessors:** US00131 (the final catalog decides what is stockable; also supplies the ≥3-per-category counts the guard asserts).
**Successors:** US00134 (a rewritten post must sit in a category that still exists — `lib/posts.ts` calls `assertCategoryRegistered` per post).

---

## 0. Decision taken at planning time

**Defer both `man-hinh-gaming` and `ghe-gaming`** (confirmed with the user, 2026-08-22). Neither is stocked, and stocking them would mean sourcing ≥6 monitors and chairs with working affiliate links — a content-sourcing project, not a remediation pass. The site ships with three well-stocked categories rather than five, two of which are empty.

Consequence: US00132 becomes a small, surgical change — delete two registry entries, add the guard that stops the situation recurring.

---

## 1. Scope

Strictly:

1. Remove `man-hinh-gaming` and `ghe-gaming` from the `CATEGORIES` registry in `lib/categories.ts`, **preserving their authored intro / metaDescription copy** in a non-exported `DEFERRED_CATEGORIES` const in the same file so re-registering later is a one-line move, not a rewrite.
2. Add a build-time guard: a registered category with fewer than `MIN_PRODUCTS_PER_CATEGORY` (3) products fails `next build`, naming the slug.
3. Add the equivalent Vitest coverage in `lib/categories.test.ts`.

**Explicitly out of scope:**

- Sourcing monitors/chairs (the deferred alternative).
- Any change to `CategoryHighlights`, `CategoryNav`, `app/sitemap.ts` or `generateStaticParams` **content** — all four already derive from the registry, which is the whole point of Scenario 2.
- Redirects / 410s for `/danh-muc/man-hinh-gaming/` and `/danh-muc/ghe-gaming/` — never deployed under the production domain (US00135 Half B has not run), so nothing was ever indexed. If Half B *has* already run when this lands, revisit — see **R3**.

---

## 2. Pre-conditions / current state

Every consumer of the registry, verified by `grep`:

| Surface | Reads | Effect of removing an entry |
| --- | --- | --- |
| `app/sitemap.ts:12` | `getAllCategorySlugs()` | `/danh-muc/<slug>/` drops out of `sitemap.xml` |
| `app/danh-muc/[category]/page.tsx:17` | `getAllCategorySlugs()` in `generateStaticParams` | page is no longer pre-rendered; the route's `not-found.tsx` handles the slug (SSG → 404) |
| `components/CategoryHighlights.tsx:7` | `Object.keys(CATEGORIES)` | homepage tile disappears |
| `components/CategoryNav.tsx:11` | `Object.values(CATEGORIES)` | sibling-nav link disappears |
| `app/san-pham/page.tsx:23`, `app/bai-viet/page.tsx:23`, `components/PostCard.tsx:9` | `getCategoryLabels()` | filter option disappears; no post/product uses the deferred slugs, so no label lookup goes missing |
| `lib/breadcrumbs.ts:25,33,43` | `getCategoryMeta()` | only called for a product's/post's own category — none use the deferred slugs |
| `lib/products.ts` / `lib/posts.ts` | `assertCategoryRegistered()` | would fail the build if any product/post used a deferred slug. **Verified: none does** (catalog categories are `chuot-gaming`, `tai-nghe-gaming`, `ban-phim-gaming`; post categories are the same three) |

So Scenario 2 is satisfied *by construction* — this is the payoff of the existing "categories are registered in one place" convention. No per-surface edit is required, and the plan must resist inventing one.

**What does not exist yet:** anything that notices a registered-but-empty category. That is Scenario 3, and it is the only real engineering in this story.

## 3. Approved Decisions

| # | Decision | Choice | Rationale |
| --- | --- | --- | --- |
| D1 | Resolution | Defer both | Operator decision; see §0. |
| D2 | Preserve the copy | Move both entries into `const DEFERRED_CATEGORIES: Record<CategorySlug, CategoryMeta>` in `lib/categories.ts`, with a comment naming the re-registration condition (≥3 products) | The 100–200-word Vietnamese intros are real work; deleting them outright means rewriting later. Keeping them adjacent to `CATEGORIES` makes the re-add obvious and keeps a single source of truth for category copy. |
| D3 | Guard threshold | `export const MIN_PRODUCTS_PER_CATEGORY = 3` in `lib/categories.ts` | Spec Scenario 1 says "at least 3 products". One constant shared by the guard, `lib/products.test.ts` (US00131) and any future check. |
| D4 | Guard implementation | `export function assertCategoriesStocked(products: Product[]): void` in `lib/categories.ts` — throws naming **every** under-stocked slug and its count | Same fail-loudly-name-the-slug style as `assertAffiliateUrl` / `assertCategoryRegistered`. Reporting all offenders at once beats one-per-run. |
| D5 | **Where the guard is called** | From `generateStaticParams()` in `app/danh-muc/[category]/page.tsx` — **not** from inside `getAllProducts()` | Critical: `scripts/ingest/dedupe.ts` calls `getAllProducts()` to seed its index. A throw inside the loader would make the ingest CLI crash whenever a category is under-stocked — i.e. exactly when you are running it to *fix* that. `generateStaticParams` is a real `next build` gate that scripts never import, and it is the precise place an empty category page would otherwise be emitted. |
| D6 | Type import direction | `assertCategoriesStocked` takes `Product[]` as a parameter; `lib/categories.ts` imports only the **type** from `@/types` | Keeps the existing dependency direction (`products.ts` → `categories.ts`) and avoids a runtime import cycle. |
| D7 | Test coverage | New `lib/categories.test.ts`: (a) a registry entry with 0 products throws naming it; (b) with 2 products throws; (c) with 3 passes; (d) multiple offenders are all named in one message; (e) the live registry + live `getAllProducts()` passes | Scenario 3 asks for build *or* test enforcement; do both — the build gate is authoritative, the test gives a fast local signal and documents the rule. |
| D8 | `sitemap.xml` assertion | Add a case to the same test file asserting every `/danh-muc/` entry emitted by `app/sitemap.ts` has ≥3 products | Scenario 1 is phrased in terms of sitemap URLs; asserting it directly is cheap and states the intent literally. |

## 5. Step-by-step execution order

1. Branch `feat/US00132` (after US00131 merges — the guard asserts counts the catalog work produces).
2. Write `lib/categories.test.ts` first; cases (a)–(d) drive `assertCategoriesStocked`, case (e) fails until the registry is trimmed.
3. Implement `MIN_PRODUCTS_PER_CATEGORY` + `assertCategoriesStocked` in `lib/categories.ts`.
4. Move the two entries to `DEFERRED_CATEGORIES`.
5. Wire the call in `generateStaticParams`; verify `next build` **fails** if you temporarily re-add a deferred entry (prove the gate works, then revert).
6. `npm run typecheck && npm run lint && npm test && npm run build`; confirm the build output drops from 33 static pages to 31 and that `sitemap.xml` no longer lists the two slugs.
7. Browser check: homepage category tiles (3, not 5), `/danh-muc/chuot-gaming/` sibling nav, `/danh-muc/man-hinh-gaming/` → 404, `/san-pham/` + `/bai-viet/` filter panels show 3 categories.
8. Docs; PR `feat/US00132` → `main`.

## 9. Risks / open items

- **R1 — The guard blocks a legitimate work-in-progress.** Registering a category *before* stocking it now fails the build. That is the intent, but it means the correct order is always "ingest products → register category". Documented in `CLAUDE.md` (§8) and in the thrown message itself.
- **R2 — Guard placement drift.** If someone later moves `assertCategoriesStocked` into `getAllProducts()` "for consistency", the ingest CLI breaks in a confusing way. Mitigated by an explicit comment at the call site and in `CLAUDE.md`.
- **R3 — Ordering vs. US00135 Half B.** If the production domain were already live and crawled, deleting two indexed category URLs would need 410/redirect handling the SSG-only site cannot serve. Currently moot (nothing deployed under a real domain). **Land US00132 before US00135 Half B.**
- **R4 — Category count vs. perceived breadth.** Three categories is a thinner-looking storefront. Accepted: three stocked categories beat five with two soft-404s, and the copy is preserved for a one-line re-add.
- **R5 — `DEFERRED_CATEGORIES` going stale / unused-export lint.** Keep it non-exported but referenced in a comment, or export it and assert in `lib/categories.test.ts` that no slug appears in both maps — pick whichever keeps `eslint` quiet; prefer the test-asserted export.
