**Status:** Done

**Scope note (post-approval):** The 2026-08-25 product-owner decision (recorded in `docs/specs/F0013.md`) deleted the 5 posts with broken covers outright instead of repointing them — narrowing this story's actual scope to §1 items 3–5 (the build-time guard, the `og:image` dimension fix, and the duplicate-cover test). Items 1–2 (repoint 5 covers, delete 2 orphans) were already satisfied by that deletion before this branch started; verified via `grep` in step 6 below with zero hits.
**Feature:** F0013 — Launch Content Remediation
**Spec ref:** `docs/specs/F0013.md` § US00133
**Predecessors:** US00131 — **the only hard dependency**: replacement covers are product images whose filenames are renamed there, so this story must consume the final slugs. **Successors:** US00134 (every rewritten post must carry a cover this guard accepts).

## 1. Scope

Strictly:

1. Repoint the 5 broken `coverImage` values at real product images, one distinct image per post.
2. Delete the two orphan 1×1 files, `public/static/images/products/logitech-g102-lightsync.jpg` and `keychron-k2-v2.jpg`.
3. Add a **build-time cover-image assertion** to `lib/posts.ts`: the path must be root-relative, resolve to a file under `public/`, parse as an image, and be ≥600px on its shorter side — failing `next build` non-zero, naming the post slug **and** the offending path.
4. Fix the **false `og:image` dimensions**: `lib/seo.ts::buildPageMetadata` currently declares `width: 1200, height: 630` for *every* image, including 1:1 product photos. This is the metadata half of Scenario 4 and is a real bug independent of the 1×1 files.
5. Add a Vitest case asserting no two posts share a `coverImage` (Scenario 2).

**Explicitly out of scope:**

- Producing bespoke 1200×630 blog artwork (`public/static/images/blog/` is empty and stays empty) — the spec's own edge case prescribes reusing the post's primary product image.
- Post prose / word counts — **US00134**.
- Applying the same existence guard to `product.images[]` — worth doing, but it belongs with the catalog story; **US00131**'s `lib/products.test.ts` covers it at test level. Noted in §9/R4 as a follow-up.

## 3. Approved Decisions

| # | Decision | Choice | Rationale |
| --- | --- | --- | --- |
| D1 | Replacement covers | Each post takes the image of **its own** lead product — the one it embeds (or will embed in US00134) — never another post's cover | Spec §5 edge case, verbatim. Ties the hero to the article's subject and keeps Scenario 2 true by construction. |
| D2 | Assignment (slugs shown pre-US00131; use the **final renamed** paths) | `chuot-gaming-cho-fps` → Razer Viper Mini · `chuot-gaming-khong-day-tot-nhat` → Razer Viper V3 Pro SE · `chuot-gaming-rgb-dep` → Logitech G502 HERO · `tai-nghe-gaming-kiem-tra` → E-Dra EH404 (7.1 surround — matches the article's subject) · `ban-phim-gaming-co-switch-tot-nhat` → a keyboard **newly ingested in US00131** (the DAREU is already taken) | Each is topically apt, and the five are pairwise distinct and distinct from the three healthy covers → all 8 unique. |
| D3 | Dimension reading | Add the `image-size` package as a **`dependency`** and wrap it in a new chokepoint module `lib/image-meta.ts` | The stager (`scripts/ingest/images.ts`) can produce `jpg/png/webp/avif`. Hand-rolling a header parser is easy for JPEG/PNG, awkward for WebP and genuinely bad for AVIF (ISOBMFF) — a false build failure on a valid AVIF cover would be worse than the dependency. Regular dependency, not dev: `lib/posts.ts` is in the app import graph even though the call only ever runs at build. |
| D4 | Threshold | `export const MIN_COVER_IMAGE_SHORT_SIDE_PX = 600` in `lib/image-meta.ts` | Spec wording ("at least 600px on its shorter side"), one constant, one home. |
| D5 | Guard location | `assertCoverImage(coverImage, slug)` in `lib/posts.ts`, called per post inside `getAllPosts()` right after `assertCategoryRegistered` | Mirrors exactly how `lib/products.ts` guards product data — same file, same position, same message shape. `lib/posts.ts` already does `fs` work, so this introduces no new I/O class. |
| D6 | Memoisation | `lib/image-meta.ts` caches `path → {width,height} \| Error` in a module-level `Map` | `getAllPosts()` is called many times across a build (listing, each detail page, sitemap, related posts). Without a cache the guard re-reads 8 files on every call. |
| D7 | Duplicate-cover check | **Test-only** (`lib/posts.test.ts`), not a build throw | Scenario 3 demands a *build* failure only for broken/missing/undersized covers. Duplicates are an editorial rule; a hard build failure would also fight `scaffold:post`, which legitimately picks a cover from a product that may already be in use (US00126 D8 wanted a warning there, not a block). |
| D8 | `og:image` dimensions | `buildPageMetadata` resolves real dimensions through `lib/image-meta.ts` for root-relative images that exist under `public/`, and **omits** `width`/`height` when they cannot be resolved (external URL, unreadable) | Truthful metadata. Omitting is safe — crawlers fetch and measure — whereas a wrong declaration is what the audit caught. Cheap because D6 caches and D3's helper already exists. |
| D9 | Alternative considered & rejected for D8 | "Emit `1200×630` only for `DEFAULT_OG_IMAGE`, omit otherwise" | Simpler, and it does fix the lie — but it throws away information the build already has. D8 costs ~10 extra lines. Fall back to this if D8 turns out to slow the build measurably. |
| D10 | Error message shape | `[content] <post-slug>: coverImage "<path>" <reason>.` where reason is `does not exist under public/` / `is not a readable image` / `is 1x1, below the 600px minimum on its shorter side` | Scenario 3 requires both the post slug and the path. Matches the `[content] …` prefix already used by `validatePostFrontmatter`. |

## 4. Files to create / modify

### 4.1 Create

| Path | Purpose |
| --- | --- |
| `lib/image-meta.ts` | The one place that reads image dimensions. Exports `MIN_COVER_IMAGE_SHORT_SIDE_PX`, `readImageSize(publicRelativePath)` → `{width,height}` or `null` (resolves against `process.cwd()/public`, memoised per D6, `null` for non-root-relative/missing/unreadable), and `assertMinShortSide(path, slug, min)`. No JSX (lib/ rule). |
| `lib/image-meta.test.ts` | Vitest, fixtures **synthesised at runtime** into a temp dir (a valid PNG is ~70 bytes of signature + IHDR + IDAT + IEND, so no binary blobs enter the repo): 800×800 PNG passes; 1×1 PNG fails with the dimension message; a `.jpg` containing text fails as unreadable; a missing path returns `null`; the memo cache avoids a second `fs` read (spy on `fs.readFileSync`). |

## 9. Risks / open items

- **R1 — Ordering with US00131.** The replacement paths are product-image filenames that US00131 renames. If US00133 is worked before those renames land, every `coverImage` written here is stale. **Do not start until US00131 is merged**; if they must overlap, write the covers using the *final* slugs and accept a temporarily red build.
- **R2 — 1:1 covers as social cards.** Product photos are square; OG/Twitter `summary_large_image` prefers ~1.91:1 and will letterbox or centre-crop. This is a *quality* compromise the spec explicitly sanctions ("reuse the post's own primary product image"). D8 at least stops the metadata lying about it. A proper 1200×630 blog-artwork pass is future editorial work, not this story.
- **R3 — `image-size` on a truncated file.** It throws rather than returning `null`; `readImageSize` must catch and convert to the D10 "not a readable image" message so the build failure is legible instead of a stack trace.
- **R4 — Products get no build-time image guard here.** A product fixture pointing at a deleted image still builds (`next/image` renders a broken frame). Covered at test level by US00131's `lib/products.test.ts`; promoting it to a `lib/products.ts` build assert using this same helper is a cheap follow-up — flag it in the PR.
- **R5 — Metadata `fs` reads.** D8 makes `buildPageMetadata` touch the filesystem. Safe under SSG (build-time only) and memoised (D6), but if any route were ever made dynamic this becomes a per-request read. Note it in the `CLAUDE.md` bullet; the SSG-only constraint (spec §10) makes it a non-issue today.
- **R6 — `scaffold:post` can now generate a build-failing post.** If a scaffolded stub's chosen cover is a product whose image is missing, the build fails rather than the CLI. Acceptable (fail-loudly), and the CLI already validates product slugs up front.
